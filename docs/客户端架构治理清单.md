# 客户端架构治理清单

本文档是 `IIoT.EdgeClient` 当前活动治理清单。长期规则以 `../../docs/总规则.md`、`客户端规则.md` 和相关专题契约为准；已完成批次的删除明细、before 证据和命令结果只在 `改动复盘与规则沉淀.md` 与 Git 历史中保留，不再混入活动入口。

## 0. 当前真值

- 当前仓库与 `IIoT.EdgeClient.slnx` 均为 32 个项目；其中 8 个是 required 测试项目，1 个是位于 `src/Testing` 的中性插件测试 fixture，Analyzer 实现项目不是测试项目。
- 当前 Release 真实发现数为 Analyzer 51、Update 17、Installer 15、Launcher 112、Module Contract 53、NonUI 590、Shell 207、UI Shared 14，合计 1059。
- `scripts/tests/edge-test-inventory.json` 登记项目集合、分类、运行时和 fixture 角色；`scripts/tests/required-test-counts.json` 只登记真实发现数。
- 已确认退役的具体工序及其源码、UI、配置、测试、solution 接线、构建/打包/发布输入已从活动树删除，不保留空工程、族共享工程、stub、alias、wrapper 或兼容入口。
- 旧的额外审批与源码冻结链已物理删除，不保留可选兼容工具或同义状态机。现行 CI 保留真实 Analyzer/project graph/build fixture、inventory、Release build、discovery、TRX 和 0 Skip 对账。
- CI 测试门禁属于本清单；生产交付/部署不属于本清单。未经当前轮明确授权，不运行发布命令，不访问或修改生产状态。
- 宿主仓与插件仓拆分由用户下一份独立计划处理；当前不创建仓库、不移动 remote、不设计双仓 CI/CD，也不把拆仓计入进度。

## 1. 通用插件边界

- 插件机制必须通用。宿主只负责 SDK、发现、装载、生命周期、manifest、capability、DataPipeline、UI 注册和包隔离，不按任何具体工序写主线规则。
- 每个生产插件必须是完整、独立构建、测试和打包的业务单元；插件族业务共享工程不得成为默认角色。跨插件通用能力只能进入 `Module.Sdk` 或经裁决的稳定 contract。
- 具体工序插件拥有自己的点位、参数、任务状态机、MES/Cloud payload、页面和业务测试。工序文档未确认前，不把任何具体插件当作宿主架构标准答案。
- 宿主、SDK、Launcher、runtime publish、bundle 与部署输入不得引用已退役插件身份；滚动复盘中的历史事实不得被扫描回生产配置。
- 当前具体插件只作产品库存，不作为宿主通用测试 fixture，也不吸收未确认的工序需求。

## 2. 中性 TestPlugin seam

`src/Testing/IIoT.Edge.TestPlugin` 是唯一宿主通用插件 fixture，必须满足：

- `IsEdgePluginTestFixture=true`、`IsPackable=false`，并位于 `src/Testing` 而不是 `src/Modules`。
- 不携带真实工序名称、点位、设备身份、MES 字段、业务状态机、生产数据或伪造在线状态。
- 只由测试项目显式构建并 stage；不得进入 Launcher profile、正式 catalog、runtime publish、bundle、安装包、稳定 release 或生产 artifact。
- 宿主/SDK 的通用发现、装载、生命周期、UI 注册和包隔离测试只使用该 fixture；不得换用另一个具体工序继续耦合宿主。
- 具体插件的页面、参数、任务状态机和 payload 只留在对应产品测试；通用 SDK 行为从产品测试抽出后，删除重复或专属副本。

中性 seam 必须覆盖：

- manifest、ModuleId、capability、ViewId、依赖声明和失败诊断；
- 插件发现、构建产物 staging、装载、真实后台服务 start/stop、停用与 DI release/dispose，且每个生命周期副作用精确一次；
- TestPlugin runtime/factory 真实创建中性 snapshot task，并通过 `IDataPipelineService` 端口入队；
- capture → `EnqueueAsync` 返回 → callback 的可观察顺序，入队仍 pending 时 callback 不触发，caller cancellation 传播且 capture/enqueue/callback 次数精确；
- 真实 Host `DataPipelineService + ProcessQueueTask` 独立证明 accepted record 到 durable consumer 的异步启动/完成、runtime 取消时 active/queued 双 item 都结清且不写任何补偿、provider 自取消按失败只写一次目标补偿；测试必须以独立 token 和确定性 idle/barrier 收口 worker，且不得把内存 drain 声称为 shutdown durable；
- `IDataPipelineService` 当前没有下游完成句柄，不得把入队 callback 伪装成 durable/MES/Cloud completion，也不得在 fake upload override 中自行添加 enqueue/completion 事件冒充真实链路；
- UI registration contract 与包内容隔离。

## 3. 测试 inventory 与计数

### 3.1 项目清单

- `edge-test-inventory.json` 必须与仓库 `*.csproj` 和 solution 项目集合精确一致。
- required 测试项目必须显式登记 `classification`、`runtime` 和 `required=true`；fixture 必须单独登记 `productionEligible=false`。
- 项目新增、删除或迁移必须在同一批次更新清单并运行 `Get-EdgeTestInventory.ps1`；不允许用目录排除或隐藏项目制造一致。
- 测试分类用于表达失效机制和运行时，不把迁移阶段名、宽泛杂项名或项目旧名当作新分类。

### 3.2 真实 runner 计数

- `required-test-counts.json` 的数值必须来自 Release 配置下真实 `dotnet test --list-tests`，不得来自源码文本匹配、历史常量或手工估算。
- 普通 CI 只验证计数，不自动改写计数文件；合法变化由维护者显式生成候选并复核完整 diff。
- 数量下降必须在本批滚动复盘中映射到物理退役或测试归口变化；专属功能测试可以随功能删除，不用 dummy、重复 case 或放宽断言补数。
- 通用插件、DataPipeline、启动、安全和取消语义不能随具体功能删除而失去全部覆盖。

### 3.3 执行对账

- 两条 Windows workflow 必须在 Release 下先执行项目图和真实正反 build fixture，再构建一次 solution，并逐项目完整执行 8 个 required 测试项目。
- 每个测试项目产生独立 TRX；最终门禁必须证明 `discovered = executed = passed`、`failed = 0`、`skipped = 0`。
- 禁止把一个测试项目拆成多个 filter 后人工加总，禁止 soft-fail、条件跳过、额外 runsettings 或 CI 运行中修改 expected count。
- required 测试中的 `Skip`、`Explicit`、条件 Skip、运行期 `Assert.Skip` 和 data-row 等价禁用语义均禁止。

## 4. 构建与生产隔离

- 生产插件打包与 runtime publish 的项目发现根必须限定为 `src/Modules`；`src/Testing` 永不属于正式插件输入。
- production catalog、bundle、Launcher profile 和 release manifest 必须只登记当前生产插件，不得通过通配扫描把测试 fixture 带入产物。
- 测试 staging 只接受本次构建登记的真实输出，复制前清空自身受控目录并保留 Config/Resources 相对结构；禁止回退到旧 `bin/Debug`、`bin/Release` 或源码 manifest 拼装混合 artifact。
- 插件包隔离测试必须拒绝 host/application/domain/presentation/test/dev/runtime-data 文件；具体 allowlist 由 `Edge客户端宿主插件分发契约.md` 约束。

## 5. 本地生成物边界

- 代码删除与验证完成后，必须清理 Edge 工作区内可再生成的 `bin/`、`obj/`、`artifacts/`、`.artifacts/`、`publish/` 和测试 staging。
- 本地清理只覆盖当前 Edge 工作区及其由本次构建产生的上层 `publish` 输出；不得扫描或删除服务器、Cloud release history、现场 Windows 安装目录、现场 SQLite 或生产数据。
- 清理后以 `find`/`rg` 证明活动树中没有退役身份、旧治理入口和对应生成物；滚动复盘与 Git 历史可保留明确标记的历史事实。
- 验证命令必须在清理前完成；清理后不得再次 build/test 重新生成这些目录，再声称本地产物为零。

## 7. CI/CD 边界

本清单允许修改 CI 中的 build、测试分类、数量/Skip、project graph、package static gate 和 workflow 运行集合。

生产 CD 不在范围内：

- 不运行 `deploy/Deploy-Changed.ps1`，包括 `-PlanOnly`。
- 不运行 `LocalPublishAndDeploy.ps1`、`PublishEdgePluginRelease.ps1` 或 stable 上传。
- 不修改 Cloud release history、服务器下载目录、现场 Windows 安装或生产数据库。

同步清理 bundle/catalog、impact mapping、preflight 和发布清单，是为了让现有 CI/CD 不再识别已删除输入；这属于源码和清单治理，不是发布。

## 8. 验证矩阵

- solution/仓库项目集合、测试清单和计数一致；
- TestPlugin 只被测试 staging 消费，生产 catalog/bundle/runtime/release 零引用；
- 活动源码、配置、测试、构建、打包、CI 和部署输入中退役身份与旧治理入口零命中；
- 本地可再生成目录在最终清理后为零；
- 滚动复盘记录范围、原因、影响面、精确命令、结果和规则沉淀位置。

## 9. 完成定义

只有同时满足以下条件，相关批次才可称完成：

- 受权删除的主体与所有活动接线已物理清零，无 stub、alias、wrapper、兼容工程或同义工具。
- inventory 与 count 文件反映真实当前资产，数量变化有 before/after 解释。
- 宿主通用插件门禁只使用中性 fixture，且 fixture 不进入生产输入。
- Release build、全部 required 测试、discovery/TRX/Skip、package/runtime/deployment policy 全绿。
- 本地生成物已在所有验证之后清理并复核为零。
- 滚动复盘和长期规则已更新；未执行 commit、push、PR、发布或生产操作时如实说明。
