## 1. 通用插件边界

- 插件机制必须通用。宿主只负责 SDK、发现、装载、生命周期、manifest、capability、DataPipeline、UI 注册和包隔离，不按任何具体工序写主线规则。
- 每个生产插件必须是完整、独立构建、测试和打包的业务单元；插件族业务共享工程不得成为默认角色。跨插件通用能力只能进入 `Module.Sdk` 或经裁决的稳定 contract。
- 具体工序插件拥有自己的点位、参数、任务状态机、MES/Cloud payload、页面和业务测试。工序文档未确认前，不把任何具体插件当作宿主架构标准答案。
- 宿主、SDK、Launcher、runtime publish、bundle 与部署输入不得引用已退役插件身份；滚动复盘中的历史事实不得被扫描回生产配置。
- 当前具体插件只作产品库存，不作为宿主通用测试 fixture，也不吸收未确认的工序需求。

## 2. 中性 TestPlugin seam

`src/Testing/IIoT.Edge.TestPlugin` 是唯一宿主通用插件 fixture，必须满足：

- `IsEdgePluginTestFixture=true`、`IsPackable=false`，并位于 `src/Testing` 而不是 `src/Modules`。
- 不携带真实工序名称、点位、设备身份、MES 字段、业务状态机、生产数据或伪造在线状态。
- 只由测试项目显式构建并 stage；不得进入 Launcher profile、正式 catalog、runtime publish、bundle、安装包、稳定 release 或生产 artifact。
- 可携带命名符合真实插件习惯的自有 `IIoT.Edge.Module.TestPlugin.Companion`；该 TestSupport 只作 fixture artifact 的内部依赖，不是新 fixture。入口程序集必须真实引用其类型，并由插件 ALC 从 staged 目录解析；默认 ALC、测试输出根或源项目 `bin` 均不得成为回退路径。
- 宿主/SDK 的通用发现、装载、生命周期、UI 注册和包隔离测试只使用该 fixture；不得换用另一个具体工序继续耦合宿主。
- 中性宿主测试使用 Alpha/Beta/Legacy 等无业务含义的 TestPlugin 身份；源码动态门禁拒绝 TestPlugin 与真实工序/极性词同时出现，具体工序测试只留在自身 runner。
- 具体插件的页面、参数、任务状态机和 payload 只留在对应产品测试；通用 SDK 行为从产品测试抽出后，删除重复或专属副本。

中性 seam 必须覆盖：

- manifest、ModuleId、capability、ViewId、依赖声明和失败诊断；
- 插件发现、构建产物 staging、装载、真实后台服务 start/stop、停用与 DI release/dispose，且每个生命周期副作用精确一次；
- TestPlugin runtime/factory 真实创建中性 snapshot task，并通过 `IDataPipelineService` 端口入队；
- capture → `EnqueueAsync` 返回 → callback 的可观察顺序，入队仍 pending 时 callback 不触发，caller cancellation 传播且 capture/enqueue/callback 次数精确；
- 真实 Host `DataPipelineService + ProcessQueueTask` 独立证明 accepted record 到 durable consumer 的异步启动/完成；runtime 取消时 Cloud/MES active+queued item 每项必须且只能一次完成下游或进入独立有界 shutdown 级联持久化，禁止无补偿 drain；总 deadline 超时必须写入可反序列化的完整 critical 恢复证据，证据失败必须使 runtime fault。级联存储成功返回即提交，返回后的取消不得双写；记录出队后的开始、完成、失败、补偿和 critical 降级日志全部 best-effort，sink/订阅者异常不得丢记录、改变已提交结果或覆盖 shutdown 主异常。provider 自取消仍按失败只写一次目标补偿；测试必须以独立 token、active/queued barrier、单总 deadline、存储返回/取消竞态、开始/完成/失败日志异常、零丢失/零重复与通道隔离收口 worker；
- MES 真实 HTTP 测试必须用 in-flight `HttpMessageHandler` 区分 caller token 取消与 transport/self-timeout；前者原样传播原 token，后者保持普通失败。
- `IDataPipelineService` 当前没有下游完成句柄，不得把入队 callback 伪装成 durable/MES/Cloud completion，也不得在 fake upload override 中自行添加 enqueue/completion 事件冒充真实链路；
- UI registration contract 与包内容隔离。

## 3. 测试 inventory 与计数

### 3.1 项目清单

- `edge-test-inventory.json` 必须与仓库 `*.csproj` 和 solution 项目集合精确一致。
- required 测试项目必须显式登记 `classification`、`runtime` 和 `required=true`；fixture 必须单独登记 `productionEligible=false`。
- 项目新增、删除或迁移必须在同一批次更新清单并运行 `Get-EdgeTestInventory.ps1`；不允许用目录排除或隐藏项目制造一致。
- 测试分类用于表达失效机制和运行时，不把迁移阶段名、宽泛杂项名或项目旧名当作新分类。

### 3.2 真实 runner 计数

- `required-test-counts.json` 的数值必须来自 Release 配置下真实 `dotnet test --list-tests`，不得来自源码文本匹配、历史常量或手工估算。
- 普通 CI 只验证计数，不自动改写计数文件；合法变化由维护者显式生成候选并复核完整 diff。
- 数量下降必须在本批滚动复盘中映射到物理退役或测试归口变化；专属功能测试可以随功能删除，不用 dummy、重复 case 或放宽断言补数。
- 通用插件、DataPipeline、启动、安全和取消语义不能随具体功能删除而失去全部覆盖。

### 3.3 执行对账

- 三仓 Windows required workflow 在 Phase 9/10 与 CI 入口另行授权后，必须在 Release 下分别构建三个 solution，并聚合 Host 26、SDK 2、Private Plugins 4 个 owner runner；不得用 Host 单仓 26 个 runner 冒充三仓合计。Pure runner 受控并行，资源 runner 串行。
- 每个测试项目产生独立 TRX；最终门禁必须证明 `discovered = executed = passed`、`failed = 0`、`skipped = 0`。
- 禁止把一个测试项目拆成多个 filter 后人工加总，禁止 soft-fail、条件跳过、额外 runsettings 或 CI 运行中修改 expected count。
- required 测试中的 `Skip`、`Explicit`、条件 Skip、运行期 `Assert.Skip` 和 data-row 等价禁用语义均禁止。
