## 0. 阅读边界与文档路由

### 0.1 继承的两条业务主线

生产数据归属与查询链由总纲定义：

```text
工序 → 设备插件 → PLC → 数据
```

上位机安装与运行链由总纲定义：

```text
上位机 → 已安装设备插件
```

- 客户端只负责第二条链的下载安装、发现、启动、运行、隔离和诊断，并为第一条链保存真实插件与 PLC 数据归属。
- 上位机不是生产数据查询层级；Launcher 卡片也不是 Cloud 查询分类。Cloud 查询仍按“工序 → 设备插件 → PLC → 数据”执行。
- 工序、设备插件、上位机、PLC 编码、显示名称和 Schema 统一继承 `BR-DOM-*`；客户端不得用当前 AP/CP 实现反向改变这条关系。
- `ClientCode` 是 Cloud 在下载时为一套具体设备插件注入的唯一业务身份，并贯穿安装、目录隔离、启动防重、Cloud bootstrap、状态和数据归属。同一个 `ClientCode` 不得再由 `ModuleId`、profile、中文名或本机生成编号建立平行身份。
- `ProcessType` 只表示工序分类；`TypeKey` 是设备插件声明的业务记录类别，一个插件版本可声明多项并分别拥有 Schema，它不是设备、插件、工序或装载身份。`DeviceId` 如为 Cloud 持久化内部键，不作为 Launcher 启动身份，也不要求人员维护。
- `ModuleId` 只作为系统维护的隐藏技术装载和包定位标识，不代替 `ClientCode`，也不让人员选择；但同一个活动安装组合中的每个设备插件仍必须具有各自唯一的 `ModuleId`，生成、安装、更新和启动校验都必须拒绝重复技术装载标识。

### 0.2 状态口径

- **已确认**：直接继承总纲中用户已确认的 `BR-*` 业务行为。
- **待业务复审**：不属于本轮已确认计划、仍需在最终统一复审中逐条确认的既有 Edge 长期规则；本轮已经确认的第 0～7 批规则可以据此实施。
- **当前现场**：仅描述当前 AP/CP 插件、PLC、MG1/MG2、弹夹或 MES 事实。
- **待裁决/冻结**：R100 设备状态候选、配方等尚未批准的业务，不授权实施；已由用户确认的 `ClientCode` 设备插件身份不再退回待裁决。

## 1. Launcher、上位机与插件运行

### 1.1 Cloud 选装和动态发现

- **继承 BR-CLOUD-003～007、BR-CLOUD-011～015、BR-EDGE-002、BR-EDGE-010、BR-EDGE-016｜已确认**：人员在 Cloud 下载界面选择一个或多个已经创建的设备插件，例如设备插件 A、设备插件 B，然后直接生成安装包；人员不再分别选择“技术插件包”和“设备”。Cloud 依据所选设备插件自动解析其 `ClientCode`、正式发布系列、真实版本和共同兼容 Host。
- **继承 BR-CLOUD-012、BR-EDGE-008、BR-EDGE-015｜已确认；BR-EDGE-014｜待业务复审**：同一个安装包可以携带多个所选设备插件；安装后每个 `ClientCode` 分别形成目录、配置、运行绑定、启动卡和诊断边界，不得因为同包安装而合成一个设备。插件版本、更新和回滚也按 `ClientCode` 独立处理的旧规则继续保留，等待统一业务复审。
- **继承 BR-CLOUD-013、BR-EDGE-002、BR-EDGE-010｜已确认**：Launcher 只根据已验证的实际安装结果动态显示设备插件卡片，不维护任何当前设备名称、极性名称或工序的固定清单。
- **继承 BR-CLOUD-014～015｜已确认**：Launcher 只接受真实发布产物及明确兼容范围；Cloud 自动选择所选设备插件共同兼容的最高已批准 `stable/win-x64` Host，下载 UI 只读展示解析结果，不允许人员手工改 Host 版本或运行时。精确 Catalog、hash、签名、文件名和事务算法由分发契约承载。

### 1.2 一个 ClientCode 一个启动项和一个进程

- **继承 BR-DOM-015～018、BR-DOM-021～022、BR-EDGE-001～004｜已确认**：一台物理上位机只有一个 Launcher；每个已安装 `ClientCode` 设备插件恰好显示一个可识别启动项，点击后启动绑定该 `ClientCode` 的独立 Shell 进程。
- **继承 BR-EDGE-005～007｜已确认**：同一个 `ClientCode` 同时只能运行一个 Shell 进程，再次点击该卡片必须阻止重复启动；不同 `ClientCode` 必须允许并发运行，一个进程失败不得影响其它设备插件。
- Launcher 必须在执行更新恢复、打开 `host.db`、迁移凭据或写任何共享状态前取得整机唯一的跨进程单实例锁；取得失败时不得启动第二个 Launcher。Shell 另按 `ClientCode` 取得自己的防重锁，Launcher 整机锁不得替代或扩大 Shell 防重边界。
- **继承 BR-DOM-003～006、BR-DOM-016～018｜已确认**：设备插件 A 和设备插件 B 代表两套现场设备，因此具有两个不同 `ClientCode`、两个独立启动项和两个可并发进程。即使插件代码或工序相似，它们在同一活动安装组合中也必须具有各自唯一的技术 `ModuleId`；`ModuleId` 唯一只防止装载冲突，不能把它提升为设备业务身份。
- profile、进程互斥量和运行绑定只是 `ClientCode` 的技术投影，不是人员维护的新业务身份；Launcher 不生成所谓“本机安装实例编号”参与设备唯一性。

### 1.3 通用 Host、Shell、Launcher 和 SDK

- **继承 BR-EDGE-009、BR-EDGE-015、BR-PLUGIN-001～009｜已确认；BR-PLUGIN-010｜待业务复审**：Launcher、Shell、Host、SDK、通用 DataPipeline、诊断、权限和持久化外壳必须业务中立；禁止按任何具体设备、极性、工序中文名或插件中文名建立业务分支。
- 每个 Shell 都复用同一套通用 Host，只在启动时绑定一个目标 `ClientCode` 并加载该设备插件。Host 只提供装载、生命周期、公共服务和通用 UI 容器，不拥有设备插件的 PLC、点位、MES、Schema、状态机或完成条件。
- **继承 BR-DOM-012～013、BR-DOM-015～016、BR-PLUGIN-015｜已确认**：新增任意现场设备时，必须新增独立设备插件包、独立发布版本链、独立业务文档、独立 `ClientCode` 和独立 `plugins/{ClientCode}` 私有目录；不修改通用 Launcher、Shell、Host 或 SDK 的名称判断。

### 1.4 宿主公共数据与设备插件私有数据

- `host.db` 只保存一台物理宿主共同使用且确实可变的数据，例如 Launcher 本地账号及安全状态、语言偏好、已安装 `ClientCode` 注册表、非密钥安装绑定账本、宿主更新策略和已应用版本状态。
- 每个设备插件必须使用独立的 `plugins/{ClientCode}` 边界保存其插件文件、私有数据库、PLC 清单、点位、MES 与业务配置、运行数据、日志、缓存、检查点和完成事实。不同 `ClientCode` 禁止共用可变业务表、配置文件、日志目录、缓存键空间或运行状态。
- Cloud bootstrap secret、upload/refresh token、MES 签名凭据、现场密码和其它密钥必须写入**实际运行 Launcher 的 Windows 账户 Credential Manager**，并按 `ClientCode` 隔离；`host.db`、`plugins/{ClientCode}` 普通文件/数据库、运行时 Binding、诊断、日志和安装审计摘要只保存不含密钥的引用或状态。本地 Launcher 账号只允许保存安全密码哈希，禁止保存明文密码。
- Credential Manager 只降低普通配置文件、备份和离线复制泄漏风险，不能防御同一 Windows 账户下的恶意进程、Windows Local Administrators 组成员或进程内存窃取；共享登录账户仍属于明确的现场安全边界，文档和审计不得把它描述成绝对隔离。
- 签名选择清单、首次安装绑定信封、插件 manifest、activation manifest、更新事务恢复日志、跨进程锁和启动 Ready 信号承担安装前验签、崩溃恢复或进程协调职责，必须继续作为独立文件证据；`host.db` 可以保存验证后的物化状态，但不得取代、伪造或吞并这些证据。
- Launcher 和多个 Shell 只通过宿主公共数据访问边界读写 `host.db`；设备插件不得直接把自身业务表写进宿主库，也不得绕过所属 `ClientCode` 访问其它插件私有存储。
- 完整 Cloud `DeviceSession`、bootstrap/Access/Refresh/Activation Token 和会话刷新能力只留在 Host 的设备出站边界。插件及其上传器只能获得不含秘密的设备身份视图和本次业务事实；不得把完整 `DeviceSession` 作为 SDK 或插件上下文传入 MES、Cloud 业务插件或任意第三方插件代码。

### 1.5 完整离线安装包与首次绑定

- Cloud 生成的安装包必须形成可在目标 Windows 上独立安装和首次启动的完整闭包：通用 Launcher/Shell/Host、所选设备插件、SDK 运行依赖、`.deps.json`、`.runtimeconfig.json`、.NET/runtime/native/DLL、Avalonia/Skia/Velopack、语言资源、页面路由、首次播种定义、配置，以及验签、更新和恢复所需材料都必须齐全。
- 包生成和安装都必须先校验所选设备插件、各自唯一 `ModuleId`、自动解析出的共同兼容最高已批准 `stable/win-x64` Host、全部传递依赖、入口文件、`.deps.json`、`.runtimeconfig.json`、Avalonia/Skia/Velopack、语言资源、页面路由、首次播种定义、真实清单、签名和 hash。任一项缺失、重复、不兼容或无法验证时必须在激活前失败；禁止依赖目标电脑预装 .NET/SDK、临时联网补 DLL，或等 Launcher/Shell 打开后才发现运行环境缺失。
- Cloud 只在生成首次安装或沿用原 `ClientCode` 的重装内容时，为每个所选设备插件一次性注入 `ClientCode`、Cloud/bootstrap/update 地址与短期 pending 凭据、加载路由、Profile、隔离目录等启动所需技术配置。PLC、点位、MES 和设备业务播种归插件所有，不由 Cloud 生成或远程修改。
- 安装配置完整性必须以“Cloud 注入值与通用 Host 默认值合并后的最终配置”为对象逐项验证；不能只检查动态路由。`ClientCode`、Cloud/bootstrap/update 地址、全部必需路径、Profile、插件目录、运行入口、凭据引用及其它必需设置必须同时存在且有效，缺任一项都不得生成启动卡。
- **安装载荷 Binding v3** 是受签名清单保护的短期安装信封，可以按 `ClientCode` 携带尚未激活的 Pending 原始凭据；普通文件中的明文副本只允许存在于权限受控分发的签名安装载荷和安装 staging，不能被原样复制到 Launcher 数据目录、`host.db`、插件目录或运行时 Binding。原凭证值随后按下一条导入 Credential Manager 的 Pending 项；原下载载荷在凭证激活或过期前仍须按权限受控材料管理，服务端在激活或过期后拒绝再次使用其中凭证。
- Installer 验证完整签名清单后，必须把每个 `ClientCode` 的原始凭据作为 Pending 项导入实际 Launcher Windows 账户的 Credential Manager，写入后立即回读，并生成只含 `ClientCode`、配置、凭据引用、`CredentialOwnerSid` 和状态的**脱敏运行时 Binding v3**。非密钥宿主登记写入 `host.db`，设备业务配置写入 `plugins/{ClientCode}` 私有数据库；全部原子提交成功后只删除 staging 中的明文副本，不得删除 Credential Manager 中的 Pending 项。该项必须保留到对应 `ClientCode` 激活成功或 Pending 过期，再按凭据协议完成清理。启动账户 SID 不一致时必须失败关闭，不得跨账户复制凭证。
- Binding Schema 必须显式版本化。Cloud 是 v3 wire schema owner；17 个字段、唯一运行配置键、路由和占位符只在[宿主插件分发契约第 5 章](./Edge客户端宿主插件分发契约.md#5-binding-v3-和凭证)定义。`EdgeBindingMaterializer` 是 v3 唯一物化器且正式调用方只能是 Installer；Launcher importer 只保留 v2 只读迁移，不得导入或补齐 v3。不认识的版本、不完整 v3、未知/重复字段、旧别名和错误占位符全部失败关闭。
- 多 `ClientCode` 安装的 Binding 文件整组写入必须原子，但 Pending 激活按 `ClientCode` 独立进行：设备 A 的 Shell 真正 Ready 只激活设备 A，不得顺带激活尚未启动或尚未验证的设备 B。某个 `ClientCode` 失败只保留其 Credential Manager Pending 项与诊断，不得回滚已安全激活的其它 `ClientCode`，文件仍不得出现半写字节。
- pending 原始凭据七天到期后只拒绝新的 bootstrap/激活，不得使已经签发且仍有效的运行会话突然失效；只有某个 `ClientCode` 的新激活成功后，才能撤销该设备插件此前的 refresh 会话。过期、失败或未 Ready 都不得提前撤旧会话。
- 首次安装完成后，现场业务配置只能由对应插件客户端修改；Cloud 日常只查询和提供正式更新，不得把查询接口变成远程写配置入口。只要 Cloud 未删除该设备插件，重装或换机继续注入原 `ClientCode`，不得创建另一套设备身份。
- 安装完成后仍须保留运行、验签、更新和恢复必需的本地清单与证据；精确文件名、Schema、签名格式、原子提交和回滚算法只在分发契约定义。

## 2. 启动、诊断和真实 UI

### 2.1 可修复启动

- **继承 BR-EDGE-007｜已确认**：一个设备插件启动失败、停止或发生业务错误，不得阻止其它设备插件启动和运行。
- **继承 BR-EDGE-011｜待业务复审**：业务配置、PLC、MES、Cloud、IO 映射或插件诊断问题应进入可登录、可诊断、可修配置的局部诊断界面。
- **继承 BR-EDGE-012｜待业务复审**：只有通用宿主、DI、框架或主窗口确实无法构造的进程级错误才可以阻止对应 Shell 打开；单个插件业务配置错误不得升级为整机不可启动。
- **继承 BR-EDGE-013｜待业务复审**：启动成功必须来自目标 Shell 的真实 Ready 事实；进程创建、旧状态缓存或外部系统在线不能冒充启动完成。
- Launcher 启动顺序固定为：Velopack 生命周期 hook → 取得 `Global\IIoT.Edge.Launcher` 整机锁 → 恢复安装/更新事务 → 恢复并迁移 `host.db` → 按 `ClientCode` 迁移旧凭据 → 校验 Binding v3、17/17 路由、最终 machine config 及凭证 SID → 校验插件 manifest/hash/精确版本 → 开放登录、设备卡片和 Shell 启动。第二个 Launcher 在 UI、数据库和共享文件写入前退出；锁创建/权限失败必须失败关闭，遗弃锁取得后仍先恢复。前七个门未全部成功时不得创建或开放交互主窗口。
- 旧明文会话迁移必须先验证源文件、在 Credential Manager 写入并回读成功、再提交 `host.db` 引用和迁移完成标记，最后才移除明文源；任一步失败都保留原始可恢复证据、不得打印密钥，也不得创建空凭据或假完成标记。
- 插件更新崩溃恢复必须能够在 `host.db` 不可用时读取独立恢复日志并完成回滚或明确阻断；迁移中断、旧文件损坏、凭据导入失败或身份冲突时进入受限修复界面，禁止覆盖未结束更新事务、禁止开放受影响 `ClientCode` 卡片，但不得无故拖停已经验证安全的其它卡片。
- 生产环境缺少有效 `ClientCode`、运行时 Binding 或目标插件时必须在数据库、网络和插件加载前失败关闭，禁止使用 `EdgeHostDefault`、空 `Modules.Enabled`、静态 Default catalog 或其它默认 profile 启动空 Shell。开发入口必须使用单独且显式的 fixture 标记，不得进入生产安装包、Launcher 发现或恢复链；生产包不得包含可启动的 `launcher.profiles.json` Default 卡。
- 具体 Ready 握手、原因码、异常脱敏和恢复算法继续由第 5 章稳定规则及对应技术契约约束，不在业务正文重复。

### 2.2 真实 UI

- **继承 BR-EDGE-013、BR-DATA-004、BR-PLUGIN-013｜待业务复审**：Launcher 和 Shell 只能显示真实安装、运行、PLC、数据、诊断和权限事实；无真实数据时显示空态。

- 插件生产页面由当前插件注册，只展示该插件真实采集、真实完成或真实持久化的数据；Host 标准页面只能提供通用容器和空态。

## 3. 插件本地数据、PLC 缓存、Cloud/MES 与补偿

### 3.1 插件私有数据库与首次播种

- **继承 BR-PLUGIN-001～005｜已确认**：每个 `ClientCode` 设备插件独立拥有自己的数据库 Schema、EF Core migration 历史、播种完成记录和事务边界；PLC、点位、MES、业务参数、任务绑定和完成条件由该插件定义。Host 只提供隔离的数据库能力与生命周期，不得直接读取或写入插件业务表；Cloud、SDK 或其它插件也不得代为迁移、播种或提交事务。
- 初始播种只允许在该 `ClientCode` 的私有数据库首次创建且尚无播种完成记录时执行一次。一次成功后，普通启动、重启、断网重启、Launcher 重开和插件进程恢复都不得再次执行初始播种。
- 后续 Schema 变化只能通过显式、版本化迁移增加所需结构或数据，不能重跑初始播种、清空重建或覆盖具有配置权限的本地 `Admin` 已经保存的配置。迁移失败必须保留原库并隔离当前 `ClientCode`，不得影响其它设备插件。
- 重装或换机仍使用 Cloud 原有 `ClientCode`；若目标目录确实是新的空私有数据库，可在该新库完成一次首次播种，但不得据此在 Cloud 新建设备或改变原设备身份。

### 3.2 PLC 权威配置、实时缓存与 Cloud 读取 API

- **继承 BR-PLUGIN-004、BR-PLUGIN-008～009、BR-DATA-015～019｜已确认**：PLC 清单、稳定 `PlcCode`、名称、IP、端口、协议和其它持久配置以所属 `ClientCode` 插件私有数据库为唯一权威；PLC 当前连接与运行状态以该插件当前 runtime 的实时状态缓存为事实。两者不得混成另一套 Cloud 配置源。
- **继承 BR-CLOUD-018～025、BR-PLUGIN-008｜已确认**：插件通过 SDK 标准快照端口把“PLC 列表与状态总览”交给通用 Host，Host/Edge 再通过正式上传链写入 Cloud 投影；Cloud 查询自己的投影并支持按 `PlcCode` 展示单台 PLC 明细。Cloud 不直连插件进程、不调用插件本地 API、不访问插件数据库，也不得借状态链修改现场配置。
- PLC 稳定配置使用按 `ClientCode` 隔离的 cache-aside：缓存命中直接读缓存，缓存未命中才回源私有数据库；禁止每次状态上报都重新查询数据库。具有配置权限的本地 `Admin` 在插件内修改配置时，批准的缓存双删/双杀顺序固定为：写数据库前先提升目标配置版本并使该 `ClientCode` 的旧缓存失效；随后在数据库事务中提交配置及新版本，并从数据库重载这份已提交值；提交后再次使缓存失效，再把重载的已提交值按新版本写入缓存。所有缓存回填必须比较版本或等价 fencing token，早于本次写入启动的旧并发读取不得在任一步之后把旧值回填。
- PLC 连接、故障、采集时间等实时状态由 runtime 持续刷新，不得为每次 Cloud 上报重新构造数据库事实；API 返回的总览必须把权威稳定配置与同一 `PlcCode` 的当前运行快照合并，并标记采集时间和新鲜度。
- 监控页等 500ms 热循环只能读取已经预载并按版本发布的内存快照；PLC 稳定配置、任务绑定、IO 映射和 recovery 状态不得在每个 tick 查询 SQLite，也不得形成“全 PLC 列表 + 每 PLC 多次查询”的 N+1。配置变化只经写入事务和版本栅栏刷新内存快照。
- PLC 清单读取结果必须显式区分 `Authoritative` 与 `Unavailable`。缓存缺失或损坏时先回源数据库；数据库仍不可读、迁移未完成或快照无法证明完整时只能返回 `Unavailable` 并跳过本轮权威上报，禁止用空数组代替失败。
- 只有具有配置权限的本地 `Admin` 明确保存“该插件当前没有任何 PLC”并产生新的配置 revision 后，才能上报权威空清单。Cloud 收到 `Unavailable`、过期或无 revision 的结果必须保留最后一次有效 PLC 投影，不得清空现有 PLC 状态。
- 本节的 PLC 状态总览不是生产数据查询。历史生产数据仍由 Cloud 按“工序 → 设备插件 → PLC → 数据”查询，客户端 API 不承担历史业务查询源。

### 3.3 真实完成事实与归属

- **继承 BR-DATA-001～005｜已确认/待业务复审**：每条生产事实必须携带所属插件和 PLC；不同插件、不同 PLC 不得串线，缺失字段不得用默认假值补齐。
- 生产记录和产量只能来自插件定义的真实完成事实；PLC 当前值、连接状态、仅入队、仅写入缓冲或 Cloud/MES 上传结果都不能冒充业务完成。
- 每条完成事实必须携带本插件版本已经声明的 `TypeKey`；框架只用它选择业务 Schema，禁止以 `ModuleId` 或 `ProcessType` 替代，也禁止声明之外的类别进入上传链。
- 插件内部多 PLC 的任务、状态、检查点、完成事实和幂等身份继续按 `BR-PLUGIN-012` 隔离。

### 3.4 Cloud/MES 双链路

- **继承 BR-DATA-006～010｜已确认**：Cloud 和 MES 可以消费同一不可变完成事实，但身份、probe、gate、queue、retry、fallback、deadletter、成功和失败语义必须分离。
- Cloud 使用当前 `ClientCode` 设备插件的 Cloud bootstrap、授权和上传上下文，MES 使用该插件自己的 MES 身份；Cloud 内部 `DeviceId` 或令牌不得变成人员再次维护的设备身份，也不得与 MES 身份互填。
- SDK `2.0.13` 中正式 v3 MES 插件只能实现 `IProcessMesUploaderV3`，并只接收 `DevicePluginUploadContext(DevicePluginIdentity)`。该身份视图只含 `ClientCode/ModuleId/ProcessType`，`CompletionId/TypeKey` 来自完成记录；插件 DI 不导出 `IDeviceService`。`IProcessMesUploader/ProcessUploadContext` 只保留 v2 ABI 并标记废弃，Host 不得对正式 v3 插件回退 legacy 接口。
- Cloud 成功不能证明 MES 成功，MES 成功不能证明 Cloud 成功；任一通道失败不得阻止另一通道。客户端只保留短期交接与失败补传事实，不因此建立长期本地生产历史。

### 3.5 缓冲、补传和日志

- **继承 BR-DATA-008～012、BR-DATA-021～025｜已确认**：真实完成事实先写按 `ClientCode` 隔离的短期防断电交接记录；Cloud bootstrap 或 MES gate 未就绪时，各自进入独立补偿链。补传保留原 `ClientCode`、PLC、`TypeKey`、完成事实和幂等身份，真实成功后删除本通道记录，第 20 次失败转本通道 deadletter。
- 自动补传周期可配置，默认 30 分钟；对应 gate 从不可用恢复时立即触发一轮。Cloud 默认每批领取 100 条，MES 默认领取 5 条并按目标能力批量或逐条发送。
- 短期交接在所有目标完成直传或可靠转交对应补传链后立即删除；它不是历史数据库。正常上传成功的生产事实不再写长期 SQLite 或 Excel，客户端历史页面与“今日历史产量”不再把本地库当作历史真值，历史只查 Cloud。
- 日志文件归档和 SQLite 待补传缓冲是不同事实。Cloud 不可用不得中断本地日志；补传入队、retry、fallback、deadletter 或人工重入队均不得记录为上传成功。
- 具体队列、SQLite、重试次数、事务、关机持久化和人工恢复算法属于第 5 章受保护规则和技术实现，不在业务正文形成第二套定义。

### 5.1 Host、Launcher、安装与启动（HL）

#### HL-ARCH-001：客户端必须只有一个通用宿主框架

- Launcher、Shell、共享运行时、通用 DataPipeline、诊断、权限和持久化外壳必须保持业务中立。
- AP、CP 等当前具体设备业务只能通过外部插件扩展，禁止复制工序专属 Host、Shell 或 Launcher。
- 所有设备插件启动项复用同一份通用 Shell/Host/SDK 运行库，但每次启动只绑定一个目标 `ClientCode`；不得把多个 `ClientCode` 合并成一个业务进程，也不得为每个工序复制一套宿主程序。profile、互斥量等技术字段只能由 `ClientCode` 派生，不能成为平行业务身份。
- Host、SDK 和插件不得互相复制具体工序源码、参数、状态机或外部协议实现。

#### HL-PROFILE-001：同一台机器允许同时运行 AP 和 CP

- 一台物理上位机由一个 Launcher 展示和管理全部已安装设备插件；每个 `ClientCode` 恰好贡献一个可识别启动项和一个运行绑定。
- 设备 A、设备 B 等同工序现场设备具有不同 `ClientCode`，不是同一个 `ModuleId` 或 profile 下的两个运行实例。
- 同一 `ClientCode` 同一时刻只允许一个 Shell 进程，重复点击必须被阻止；不同 `ClientCode` 必须允许并发启动和运行。
- 一个 `ClientCode` 的启动、退出、故障或诊断不得改变另一个 `ClientCode` 的运行结果；物理宿主和 Launcher 不生成新的业务实例号参与该判断。
- AP/CP 只是当前现场插件示例，Launcher、Shell 和 Host 不得据此形成固定插件清单。

#### HL-SOURCE-001：生产插件只能来自 Cloud 统一链路

- 首装由人员在 Cloud 选择一个或多个设备插件；Cloud 自动解析每个设备插件的正式发布系列、真实版本和共同兼容 Host，人员不分别维护“设备”和“技术包”两次选择。
- Cloud 必须把通用 Launcher/Shell/Host、已选设备插件、`.deps.json`、`.runtimeconfig.json`、.NET/runtime/native/DLL、Avalonia/Skia/Velopack、语言资源、页面路由、首次播种定义、配置以及验签、更新和恢复材料组成完整离线闭包；任一必需依赖缺失必须阻止生成，禁止让客户端首次打开后才发现缺运行时、DLL、资源、路由或初始化定义。
- 后续插件更新只能使用 Cloud 为当前上位机已选或已安装插件返回的正式 catalog、版本和下载地址。
- Launcher 只负责激活、绑定和更新 Cloud 已选插件，禁止从纯 `Default` 状态自行新增尚未被 Cloud 选择的插件。
- 禁止通过手工投放目录、扫描 fallback、未绑定 catalog、本地 URL、样例包或其它旁路让未被 Cloud 选择的插件进入生产 profile。
- Launcher activation 只能消费经验证的 Cloud 已选设备插件清单，并按唯一 `ClientCode` 物化到 `plugins/{ClientCode}`；精确文件、Schema、签名和原子目录算法由分发契约定义。输入缺失、损坏、版本不支持、`ClientCode` 重复或为空时必须失败关闭，只保留不含业务插件的维护入口。
- `Default` 如为开发调试保留，必须使用独立显式开发标记且不进入生产安装包、Launcher 发现或恢复链；生产维护、登录和诊断也必须先具有有效 `ClientCode` 与运行 Binding，不得启动空 Shell。

#### HL-CLOUD-001：Cloud 注入必须是下载时一次性永久配置

- 继承 `BR-CLOUD-006`、`BR-CLOUD-011`、`BR-CLOUD-012`、`BR-CLOUD-033`～`BR-CLOUD-035`：Cloud 在生成首次安装或沿用原 `ClientCode` 的重装内容时，为每个所选设备插件分别注入 `ClientCode`、Cloud/bootstrap/update 地址、短期 Pending 原凭证、加载路由、运行绑定和隔离目录，并提供真实安装内容；不同 `ClientCode` 的值不得串用。普通文件中的 Pending 明文副本只存在于权限受控的签名安装载荷和受控 staging；Installer 验签后把原凭证值导入 Credential Manager Pending 项，正式运行配置只保存脱敏引用。
- Cloud 首装技术配置必须经受控安装链到达客户端，先完整校验再原子落盘；失败形成目标 `ClientCode` 诊断，不得应用半份配置、借其它插件默认值补齐或在普通查询期间远程重写。
- 客户端断网重启必须继续读取已经成功落盘的正式配置，不能把 Cloud 在线作为读取既有配置的前提。
- PLC、点位、MES 和设备业务初始值由插件自有播种和私有数据库管理，不由 Cloud 下载链注入；首次安装后，这些现场业务配置只能在对应插件客户端修改，Cloud 查询接口不得远程改写。
- Installer 完成签名与完整性验证后，必须把 `BootstrapSecret` 等原凭证按 `ClientCode` 导入**实际运行 Launcher 的 Windows 账户 Credential Manager**，运行时 Binding、`host.db`、插件普通文件/数据库和审计只能保存脱敏引用或状态；禁止把安装信封原文复制进正式目录。只要 Cloud 未删除该设备插件，重装或换机仍注入原 `ClientCode`，不得生成新的本机设备编号；精确 Schema 与安全处理由分发和上传技术契约定义。

#### HL-META-001：插件静态元数据不得成为第二配置源

- `plugin.json` 只能声明隐藏技术加载标识、显示信息、入口、版本、Host 兼容范围、正式配置 Schema 路径、初始播种版本和静态能力；其中 `ModuleId` 如保留，只供系统加载和包定位，不代表工序、设备或启动身份，也不让人员维护；同一活动安装组合中的重复 `ModuleId` 必须在激活前拒绝。它不得直接承载 PLC、IO、MES 或 Business 运行值。
- activation/profile 只能描述固定 Host 入口和由 `ClientCode` 派生的运行绑定，不得生成独立 `InstanceId` 业务身份，也不得重复保存设备、IO 或本地参数默认值。
- 插件可以携带自身 PLC/IO、MES 和 Business 初始播种定义，但只在该 `ClientCode` 私有数据库首次创建时执行一次；后续版本变化通过显式迁移处理，禁止普通启动重复播种。
- 旧 `*.module.json` 不再是运行配置源；即使历史包仍携带该文件，Host 也只能报告稳定诊断并忽略其全部键。
- `plugin.json`、activation、Cloud 首装绑定、`host.db` 和 `plugins/{ClientCode}` 私有数据库之间必须有明确且唯一的 owner，禁止同一参数在多处分别生效或按偶然加载顺序覆盖。
- 插件包不得携带真实 Cloud 身份、Cloud secret 或独立 Cloud 下载地址。

#### HL-LAUNCH-001：Launcher 只能激活 Cloud 已选 profile

- Launcher 必须共同校验 Cloud 选择清单、已安装 `ClientCode`、`plugin.json`、activation、运行绑定和包内技术加载标识。
- activation 目录扫描、配置物化、启动恢复 reconciliation、profile 可见性和最终启动校验必须共用同一份已启用插件选择，禁止任一阶段自行回退到目录扫描。
- activation 只能从选择清单为目标 `ClientCode` 声明的已验证 `plugins/{ClientCode}` 目录读取；目录内包绑定必须与该 `ClientCode` 一致。同名目录、重复 `ModuleId` 或其它 profile 不得冒充，选中目录、manifest 或 activation 缺失时必须形成按 `ClientCode` 隔离的稳定诊断。
- 最终启动校验必须在取得共享 launch/update 租约后、启动进程前重新读取选择清单和当前 activation，并持有租约完成 Ready 交接。缓存卡片必须绑定贡献它的 `ClientCode` 和已验证目录；profile、互斥量和启动参数都只能是该绑定的技术投影。
- 只有 Cloud 已选且校验通过的 `ClientCode` 设备插件才能贡献 Launcher 卡片并进入运行注册表；`Modules.Enabled` 如在迁移期保留，只能是内部派生结果，不能成为第二份人员选择或设备真值。
- activation 或绑定失败只能影响对应插件/profile，并形成非阻断诊断；禁止阻断 Launcher 的通用修复 UI。
- 未被 Cloud 选择、缺少绑定或身份不一致的插件不得因目录存在而自动物化、显示或激活。

#### HL-RELEASE-001：业务 Cloud 开关不得关闭客户端发布控制面

- 系统级 `CloudApi:Enabled` 只控制生产数据、日志、产能、运行心跳、设备状态和补传等 Cloud 业务数据面。
- release bootstrap、catalog、包下载和版本上报属于发布控制面；当前 `ClientCode` 存在合法首装绑定、受保护凭据和宿主更新策略时必须继续工作。运行时必须同时取得设备 bootstrap、设备 catalog、版本上报和运行心跳四条正式路径；缺任一项时该 `ClientCode` 的发布控制配置不可用，不得从 Host 默认值补齐。
- 发布控制面只能读取安装事务已经提交的正式配置：宿主公共更新策略来自 `host.db`，设备 endpoint 和其它设备业务配置来自对应 `plugins/{ClientCode}` 私有数据库，凭据原文只从实际 Launcher Windows 账户 Credential Manager 读取，脱敏运行时 Binding 只保存 `ClientCode` 与凭据引用，签名安装/更新清单继续作为文件证据。环境变量、Host 或插件包内 `appsettings`、打包 profile 和 Cloud 开关投影均不得覆盖或门控该配置。
- 发布 catalog 返回的 Host source 必须与本地正式更新源一致；不一致、缺配置、认证失败、超时、服务端错误、结构错误或非法版本均属于“无法检查”，不得伪装为 `Current` 或“已最新”。
- 业务 Cloud 关闭时运行心跳和其它业务数据面必须保持零请求，但合法的发布控制面仍执行版本比较、下载和版本上报。

#### HL-UPDATE-001：Shell 运行期间禁止更新 Host 或插件

- 任一 Shell 实例运行期间，Launcher 必须禁止替换 Host 或任何插件目录。
- 启动 Shell 与开始更新必须使用同一个跨进程原子门控，保证两者不能越过彼此的检查窗口。
- 多个 Launcher 实例、不同 `ClientCode` 并发 Shell 和后台更新进程必须共享同一门控语义。
- 更新只允许作用于 Cloud 已选且已承担当前 profile 责任的插件，禁止借更新页面安装尚未被 Cloud 选择的新插件。
- 更新失败不得删除当前可运行版本，不得改变其它插件或其它 profile 的结果。

#### HL-INSTALL-001：插件安装必须是完整事务

- 安装前必须完成下载来源、大小、SHA256/签名、压缩包边界、`plugin.json`、入口程序集、各插件技术 `ModuleId` 唯一性、自动解析的最高已批准共同兼容 `stable/win-x64` Host、activation，以及 `.deps.json`、`.runtimeconfig.json`、.NET/runtime/native/DLL、Avalonia/Skia/Velopack、语言资源、页面路由、首次播种定义、配置、验签、更新和恢复材料的完整闭包校验。
- 每个设备插件只能先写入按 `ClientCode` 隔离的 staging；校验全部通过后才能原子替换正式 `plugins/{ClientCode}` 目录。
- 共享 Launcher/Shell/Host、全部所选插件文件、Profile、非凭证 Binding 素材、安装记录、activation、`host.db` 非密钥注册、运行注册表和依赖插件集合必须作为一个完整文件组原子提交；文件组未完整成功时不得暴露任何新启动项，并保留上一可用文件组。
- 受签名安装信封中的每 `ClientCode` Pending 原凭证必须由 Installer 导入实际 Launcher Windows 账户 Credential Manager；正式运行时 Binding 只保存脱敏凭据引用和 Owner SID。Binding Schema 版本、Cloud 生成器、Installer 唯一物化器、Launcher 启动前置/v2 只读迁移器和 Host 运行消费者必须同批切换，未知版本或缺字段一律失败关闭。原子提交成功后只删除 staging 明文副本，Credential Manager Pending 项保留到该 `ClientCode` 激活成功或 Pending 过期。
- 文件组整组原子安装不等于多个设备共同激活：每个 `ClientCode` 只在自身 Shell 真实 Ready 后激活自身 Pending 并撤销自身旧 refresh 会话。设备 A 未启动、失败或 Pending 过期不得阻止设备 B Ready，也不得改变设备 B 已有效的凭据。
- 任一文件组校验或提交步骤失败必须恢复原插件目录、原安装记录和原 profile 状态，禁止留下半安装、半启用或无法回滚的组合；真实 Ready 后按 `ClientCode` 独立进行的凭据激活不适用跨设备共同回滚。
- 多插件依赖安装必须整体成功或整体回滚，禁止前置依赖已替换而目标插件失败。
- 签名选择清单、绑定信封、manifest、更新恢复日志、锁和 Ready 信号继续作为独立文件证据；不得为了数据库化而删除安装前或数据库损坏时仍必需的验签、恢复和协调材料。

#### HL-CONFIG-001：客户端本地参数必须由客户端和插件共同归口

- 每个 `ClientCode` 设备插件独立拥有配置 Schema、PLC/IO 模板、MES 参数、业务参数和初始化需求；一个 `ClientCode` 的配置不得成为另一个 `ClientCode` 的默认值。
- Cloud 只在首次下载安装时注入启动所需技术配置；插件初始播种提供该插件自己的业务初值；具有配置权限的本地 `Admin` 在对应插件客户端维护后续现场业务配置。三类数据边界固定，不能靠偶然加载顺序覆盖。
- Host 只提供通用校验、事务、持久化和诊断能力，不按插件名称解释配置，也不得用样例或其它插件数据补缺。
- 配置成功后，运行时读取经确认的插件永久配置；插件升级不得无条件覆盖现场已经保存的有效值。
- 首装完成后 Cloud 只读查询现场配置投影，不得远程修改 PLC、点位、MES 或业务参数；重新下载安装可以再次注入原 `ClientCode` 的启动技术配置，但不能借此覆盖插件私有业务配置。

#### HL-SEED-001：首次激活和 schema 升级必须幂等播种

- 每个 `ClientCode` 的插件私有数据库首次创建且没有播种完成记录时，才执行一次该插件自带的 PLC、IO、MES 和业务初始播种；Cloud 与 Host 不提供第二份播种数据。
- 播种成功必须记录版本和完成事实；此后的普通启动、重启、断网启动、Launcher 重开和进程恢复只读取正式数据，不得再次运行初始播种。
- Schema 升级必须使用显式版本化迁移，不得通过重跑播种“补数据”；新增结构或必需数据只能由该版本迁移精确处理，已有现场有效值不得被覆盖。
- 初始化必须在该 `ClientCode` 私有数据库事务边界内完成；失败保留原数据、只隔离目标设备插件并允许 Shell 进入诊断态。
- 生产首启禁止启用 `ResetBeforeImport` 或任何“先清空再导入”的 destructive reset。
- manifest、播种完成记录和迁移协议的精确格式只由分发和架构技术契约定义。

#### HL-READY-001：启动成功必须来自 Shell Ready 握手

- `Process.Start` 返回只表示操作系统创建进程请求成功，禁止直接记录“客户端启动成功”。
- Shell 必须在目标 `ClientCode` 的单进程边界已占用、对应运行绑定已加载、`plugins/{ClientCode}` 插件已发现并注册、本地迁移与首次初始化已完成或形成明确诊断、主窗口已显示后，向 Launcher 返回 Ready。
- Launcher 必须等待有超时、进程身份和 `ClientCode` 校验的 Ready 握手；目标进程提前退出、超时、`ClientCode`/进程不匹配或目标插件缺失时不得显示成功。
- PLC、MES、Cloud 离线或业务配置待修复允许返回 `ReadyWithDiagnostics`，但必须携带稳定、脱敏、可解析的原因与修复入口。
- Shell 写入 Ready 前必须合并当前后台任务快照；任一主队列、Cloud retry 或 MES retry worker 已进入 `Faulted` 时只允许返回 `ReadyWithDiagnostics`，禁止用较早的启动汇总冒充干净 Ready。
- 握手必须携带 Shell 实际进程 ID；只有与 Launcher 本次启动目标 PID 完全一致的 `Ready` 或 `ReadyWithDiagnostics` 才能记为启动成功，旧进程或其它进程写入的信号必须拒绝。
- 版本上报、外部心跳和外部系统业务健康不得作为 Ready 的必要条件。

#### HL-NONBLOCK-001：业务和配置问题不得阻断修复 UI

- Launcher 和 Shell 必须始终优先进入可登录、可诊断、可修配置的 UI。
- `host.db` 迁移、账号、更新配置、Cloud 首装绑定、插件枚举、activation、运行绑定、PLC、MES、Cloud 和 IO 配置错误必须收口为受限修复或按 `ClientCode` 隔离的局部诊断；不能安全读取账号或宿主注册表时不得开放设备启动卡，但 Launcher 修复界面仍应可进入。
- 只有 DI 容器、Avalonia 框架、主窗口或进程基础设施确实无法构造的错误才允许进入 fatal 启动错误窗。
- 非阻断不等于吞错；每个失败必须有稳定原因码、脱敏日志、受影响 profile 和修复入口。
- Launcher 局部诊断只能展示稳定原因码、安全主体、修复入口和异常类型，禁止把原始异常消息传入 UI、Ready 载荷或启动日志。

#### HL-DP-START-001：DataPipeline 三个任务必须独立启动

- 主队列 `ProcessQueueTask`、Cloud retry task 和 MES retry task 必须拥有独立启动、停止、诊断和恢复生命周期。
- 三者必须分别保存 `Stopped/Starting/Running/Stopping/Faulted` 运行状态和稳定失败码，不得再以一个 `Host.DataPipeline` 组状态覆盖。
- 一个任务启动失败不得停止已经启动的另外两个任务，也不得阻止 Shell 进入 Ready/ReadyWithDiagnostics。
- 停止超时后只有迟到停止安全成功才能解除 quarantine 并允许定向恢复；迟到停止最终失败必须继续失败关闭，禁止在旧 worker 可能未退出时重复启动。
- 本地主队列任务启动失败必须明确标记本地生产链不可用；Cloud 或 MES retry 启动失败只能标记对应外部补传链不可用。
- 运行期一个任务退出、阻塞或重启不得连带取消其它任务。
- 三个任务在启动失败或 Ready 后意外退出为 `Faulted` 时，Host 必须以有界间隔只重试对应任务，复用原服务实例；禁止忙循环、重启其它任务或要求整个 Shell 重启。进程停止必须先取消恢复监督，再按既有逆序停止服务。
- 启动失败后的停止清理超过截止时必须保持 `Faulted` 和稳定停止超时码，并继续跟踪唯一迟到停止任务；迟到停止完成前不得并发重启或重复停止，期间任何 `Stopped` 覆盖都必须在下一次有界监督中恢复为故障。只有迟到停止安全完成后才允许定向重启；永不完成时必须持续显示故障，禁止伪装为已停止或已恢复。
- 系统诊断页必须在现有刷新链中展示三个任务的实时状态、变更 UTC、稳定错误码和修复目标；故障后恢复为 `Running` 时必须消除旧错误码。页面和日志禁止显示原始异常消息。

### 5.2 完工、Cloud/MES 与补偿（CM）

#### CM-DP-001：真实完工必须进入主队列

- 每条通过 PLC、任务绑定和工序状态机确认的真实完工事实，必须生成一条唯一的 `CellCompletedRecord`。
- `CellCompletedRecord` 必须携带原始 `ClientCode`、PLC、任务、槽位和业务标识上下文；隐藏 `ModuleId` 不得代替设备插件归属。
- 无论 MES、Cloud 开关组合为何，真实完工事实都必须进入主队列。
- `UploadTargets=None` 是合法的“仅执行本地完工链”状态，禁止因为没有外部上传目标而跳过 DataPipeline。
- 只有主内存队列或完整入口持久化已经可靠接受记录时，生产任务才能提交本次状态切换。

#### CM-DP-002：本地完工链不依赖外部上传

- 主队列实际接受真实完成事实后，先写短期防断电交接信封，再分别驱动 Cloud 与 MES 目标。
- MES/Cloud 开关、心跳、身份、HTTP、业务响应、重试或死信状态不得抹去已经确认的完成事实；失败通道必须可靠转入自己的补传链。
- 入队成功只表示内存队列或短期入口持久化已接受，不等于 Cloud 或 MES 成功，也不授权写长期本地生产历史。
- 正常上传成功的数据不得继续追加 AP/CP 生产 SQLite 或 Excel；历史 UI、产量与生产记录统一从 Cloud 正式归档查询。

#### CM-DP-003：顺序不是外部链路依赖

- 主队列保持单 Reader，单条记录按已注册消费者顺序完成短期交接和 durable 出口投递。
- 短期交接、UI 当前状态、MES、Cloud 的具体 `Order` 数值属于实现细节，不得提升为业务先后依赖。
- MES 和 Cloud 必须投递到两个独立的 durable 出口 worker；禁止等待其中一个上传成功后才允许另一个出口开始。
- 任一消费者失败必须在自己的失败语义内收口，禁止中断后续消费者。

#### CM-DP-004：队列溢出必须恢复完整主链

- 主内存队列满时，必须持久保存完整 `CellCompletedRecord`、完整可反序列化 `CellData` 和原始上下文。
- 溢出记录恢复后必须重新进入完整主消费链，补齐尚未完成的短期交接回执与记录自身声明的外部目标，不得补写长期本地生产历史。
- 完整入口必须在独立的 `pipeline_ingress.db` 保存首次接受的不可变信封，并以稳定完工 ID 为每个本地 consumer 和 Cloud/MES 目标持久交接分别记录回执。
- 任一必需交接步骤失败时必须保留入口信封和已完成回执；恢复时只重试未完成项。外部目标只有真实接收成功，或已可靠落入本通道 retry/fallback/deadletter 可消费链，才能记为交接完成。
- 全部必需回执完成后才能清理完整信封，并必须保留完成 ID 墓碑，防止同一完工事实再次进入消费链。
- 禁止在队列溢出时遗漏短期入口、幂等墓碑、任一已声明外部目标或当前运行态通知。
- 禁止同一溢出记录既直接扇出 Cloud/MES，又重放完整主链而制造重复上传。
- 溢出恢复必须使用稳定幂等身份，保证本地记录和外部上传不因重放而重复。
- 完整入口持久化也失败时必须返回拒绝；生产状态机不得移除当前活动弹夹或把该次完工记为已提交。

#### CM-ROUTE-001：开关只裁剪新记录的上传目标

- 插件形成真实完工事实时，根据本插件 MES 开关和系统唯一 Cloud 开关计算 `UploadTargets`。
- MES 关闭时，新记录不得包含 MES 目标，也不得调用 MES consumer 或生成 MES 失败记录。
- Cloud 关闭时，新记录不得包含 Cloud 目标，也不得调用 Cloud consumer 或生成 Cloud 失败记录。
- 两者都关闭时，记录仍可完成插件自己的实时状态切换，但不得因此建立长期本地历史；若业务要求至少一个外部归档目标而当前目标为空，应以配置诊断明确提示。
- 禁止把 MES 或 Cloud 开关解释成“是否生成长期本地生产记录”的开关；新版本不生成这类副本。

#### CM-ROUTE-002：历史目标责任冻结

- 一条记录一旦以 MES 或 Cloud 为目标被可靠接受，该目标责任就随原记录冻结。
- 后续关闭对应开关只能暂停该目标的上传和补传，禁止删除、跳过或改投另一通道。
- 开关重新开启且门控恢复后，只恢复本通道尚未完成的记录。
- 禁止在 retry、fallback、deadletter 或人工补传时根据当前开关重新计算原记录的 `UploadTargets`。

#### CM-GATE-001：MES 与 Cloud 门控独立

- MES 只有在记录包含 MES 目标、MES 开关开启且 MES 心跳 gate 就绪时才允许调用 MES 上传。
- Cloud 只有在记录包含 Cloud 目标、系统 Cloud 开关开启且 `ClientCode → bootstrap → DeviceId/token` 门控就绪时才允许调用 Cloud 上传。
- `ClientCode + CompletionId + TypeKey` 可以作为同一不可变完成事实交给 MES、Cloud 两条通道；`ClientCode` 在 MES 中只用于本地归属与幂等关联，不授予任何 Cloud 会话能力。
- MES 只能接收不含秘密的设备身份视图和完成事实，不得读取或复用 Cloud 的 `DeviceId`、bootstrap、Access/Refresh/Activation Token、完整 `DeviceSession`、会话或 gate 状态。
- Cloud 身份和请求不得读取或复用 MES 的 `upperComputerNo`、operation code、站号、签名 Token、业务回执或 gate 状态。
- 两条通道可以复用无业务语义接口、序列化、队列或重试框架，但不得复用业务凭据、会话对象、门控或通道状态。
- 一个 gate 就绪不能证明另一个 gate 就绪。

#### CM-ISO-001：运行时链路必须物理隔离

- MES、Cloud 可以复用无业务语义的接口、基类、序列化器和持久化外壳。
- MES、Cloud 的 probe、gate、durable 出口队列、worker、SQLite、retry、fallback、deadletter、诊断状态和人工补传必须分别存在。
- MES 失败只能写入 MES 通道；Cloud 失败只能写入 Cloud 通道。
- 禁止混用数据库、表名、claim token、source table、deadletter channel、身份或诊断状态。

#### CM-ISO-002：任一失败不得影响其它效果

- MES 阻塞或失败不得阻止 Cloud 或插件当前运行态/UI。
- Cloud 阻塞或失败不得阻止 MES 或插件当前运行态/UI。
- 当前 UI 等本地非历史消费者失败不得删除或伪装 MES/Cloud 的执行结果。
- 每个出口必须独立记录成功、阻塞、失败、补传和死信结果，禁止用另一出口的状态代替。

#### CM-RETRY-001：失败数据必须先可靠落盘

- 已承担目标责任的记录遇到 gate 暂时未就绪、网络失败、超时或外部业务拒绝时，必须保存完整原记录。
- MES 写入 `pipeline_mes.db` 的独立补偿链；Cloud 写入 `pipeline_cloud.db` 的独立补偿链。
- 主 retry 不可写时进入同通道 fallback；fallback 也不可写或发生永久契约错误时进入同通道 deadletter。
- deadletter 也不可写时必须生成可恢复 critical 物理证据并显式报警，禁止静默返回成功。

#### CM-RETRY-002：自动补传必须受原通道门控

- MES 补传任务只有在 MES 开关开启且 MES 心跳恢复后才能领取 MES 记录。
- Cloud 补传任务只有在系统 Cloud 开关开启且当前 Cloud bootstrap/token 门控恢复后才能领取 Cloud 记录。
- 两个任务的周期均可配置，默认 30 分钟；对应 gate 从不可用恢复为可用时立即触发一轮。Cloud 默认每批领取 100 条，MES 默认每批领取 5 条。
- 补传必须复用记录中冻结的业务事实、`ClientCode`、PLC、任务和幂等身份。
- 补传时允许使用当前有效的目标身份、token、签名和 endpoint，但禁止重算数量、条码、开始时间、完成时间或结果。

#### CM-RETRY-003：最多自动重试 20 次，随后必须进入死信

- 单通道单记录最多执行 20 次自动补传。
- 第 20 次自动补传仍失败时，必须把完整原记录可靠转入该通道 deadletter，停止自动请求。
- 禁止通过 `DateTime.MaxValue`、隐藏状态、无限延期或其它“弃置”方式代替 deadletter。
- 禁止按 30 天或其它时间自动硬删除尚未成功、尚未人工确认的 retry、fallback 或 deadletter 数据。
- 心跳或门控恢复只能恢复未耗尽重试次数的记录，禁止自动把 deadletter 重置为普通 retry。

#### CM-RETRY-004：转入死信必须零丢失

- 必须先确认 deadletter 写入成功，才能删除原 retry/fallback 记录。
- deadletter 写入失败时必须保留原记录和失败上下文，禁止先删后写。
- retry 到 deadletter 的转移不得同时留下两个可自动消费副本。
- 死信必须保留原始 `CellDataJson`、目标通道、来源表、来源记录、失败阶段、失败原因、`ClientCode`、PLC、任务和业务标识。

#### CM-OPS-001：人工补传必须受控

- 只有具有补传权限的本地 `Admin` 可以把 deadletter 重新入队；客户端不得提供人工硬删除未成功 retry、fallback 或 deadletter 数据的入口。
- 人工重新入队必须二次确认，并记录目标通道、记录 ID、工序、PLC、任务、业务标识、操作者和结果。
- 人工重新入队必须写回原通道 retry，重置自动重试计数，并保持原始业务事实和幂等身份。
- 必须先确认原通道 retry 可靠写入，才能在同一受控转移中移除 deadletter 的可消费源记录；任一步失败都必须保留唯一可恢复原记录和诊断证据。
- 自动清理、人工操作或运维脚本均不得硬删除尚未成功的数据；后续策略变更必须另行取得用户明确授权。

#### CM-DATA-001：MES 与 Cloud 消费同一份不可变生产事实

- 同一次完工只生成一份 `CellCompletedRecord` 和一份业务 `CellData`。
- MES、Cloud consumer 必须消费该记录自身携带的同一份生产事实。
- 禁止为 MES 和 Cloud 分别采集、重新查询或重新计算数量、条码、开始时间、完成时间、结果、PLC 或槽位。
- retry、fallback、deadletter 和人工补传必须保存并恢复同一份原始生产事实。

#### CM-DATA-002：允许目标协议不同

- Cloud 可以添加 `DeviceId`、request ID、幂等键、schema version 和 Cloud 授权信息。
- 新完成事实具备 `ClientCode + CompletionId + TypeKey` 完整身份时进入 `schemaVersion=3` 批次，并由 Cloud 按设备实际安装插件版本的能力 Schema 校验；现有 AP/CP 旧记录仍按真实完整性分别进入严格 v2 或历史 v1 兼容批次。三种版本必须独立分批，禁止为了升级版本补造身份、字段或把旧记录伪装成 v3。
- 产能 Cloud 适配器只在当前 PLC 配置能够可靠解析稳定代码和真实名称时发送 v2 的 `processType/plcCode/plcName`；AP/CP 无可靠质量源时发送可空 `okCount/ngCount`。无法确认真实名称的旧缓存继续按 v1 原身份发送，禁止把历史别名或代码冒充名称。
- 产能固定为完工弹夹数：每个有效 `CellCompletedRecord` 只增加 1，禁止使用 `punchingQuantity` 替代。过站记录与半小时产能缓存是两条独立事实链，只允许核对，不得互相补数或伪造。
- MES 可以添加 `upperComputerNo`、operation code、station number、timestamp、sign 和 MES 请求结构。
- 两端字段名称、信封和身份不同是协议差异，不代表允许改变生产事实。
- 目标适配器只能进行协议映射、格式转换和身份补充，禁止产生第二份业务真值。

#### CM-DATA-003：AP/CP 使用弹夹条码

- AP/CP 是模切工序，一条完工记录表示一个弹夹生命周期。
- AP/CP 当前业务唯一标识是 `ClipNo`，面向人员的名称必须使用“弹夹号”或“弹夹条码”。
- AP/CP 不得伪造不存在的电芯条码。
- 通用框架可以使用“业务唯一标识”；只有真实存在单电芯条码的其它工序才能记录“电芯条码”。

#### CM-LOG-001：每条业务记录必须可追溯

- MES、Cloud 直传成功、直传失败、补传成功、补传失败、进入死信和人工重新入队都必须能定位到单条业务记录。
- 日志至少包含：目标通道、`ClientCode`、PLC、工序、任务或槽位、业务唯一标识、执行阶段和结果。
- 直传、补传、阻塞、死信和人工恢复必须统一携带稳定 `CorrelationId + PlcCode + TaskKey + BusinessId`；AP/CP 的 `BusinessId` 即当次弹夹号。
- AP/CP 日志的业务唯一标识必须是弹夹号。
- 批量上传可以增加批次摘要，但不能只记录数量而无法追溯批次中的每个弹夹号。

#### CM-LOG-002：上传成功必须来自真实接收结果

- “MES 上传成功”必须表示 MES HTTP 调用和 MES 业务响应均确认接收成功。
- “Cloud 上传成功”必须表示 Cloud 接口返回正式成功结果。
- 已入队、已投递出口、已写 retry、已写 fallback 或已重新入队都不得记录为上传成功。
- 一个目标成功不得输出另一个目标成功。

#### CM-LOG-003：失败、阻塞和恢复必须区分

- 开关关闭、心跳未就绪、bootstrap/token 未就绪属于 `Blocked`，不能伪装成成功或普通业务失败。
- HTTP、网络、超时、业务拒绝、序列化、持久化和容量问题属于对应失败阶段。
- 补传恢复、死信转移和人工重新入队必须输出明确恢复信息。
- 日志订阅者异常不得改变上传、持久化或补偿结果。

#### CM-LOG-004：日志不得泄露敏感信息

- 禁止输出 MES 签名 token、sign 原文、Cloud token、bootstrap secret、完整敏感 URL 或响应中的敏感数据。
- 允许输出经过约束的原因码、HTTP 状态、业务状态、异常类型和脱敏摘要。

### 5.3 PLC 运行与当前模切细化（PLC）

> 本节同时包含通用 PLC 隔离规则和当前 AP/CP 的实现细化。凡出现 AP/CP、MG1/MG2、弹夹、R100、固定地址、固定状态码或固定 PLC 数量，均只按 `BR-CURRENT-*` 或冻结候选解释。

#### PLC-SEED-001：首次激活必须播种配置，但默认不得连接 PLC

- 当前 AP/CP 插件只在各自 `ClientCode` 私有数据库首次创建时，由插件自身一次性播种 PLC 设备、IO 映射和 MG1/MG2 任务绑定；Cloud 与 Host 不提供第二份业务播种。
- 新播种的 PLC 设备必须默认关闭，新播种的 MG1、MG2 任务绑定必须默认启用；具有配置权限的本地 `Admin` 完成现场地址、端口和 IO 核对并启用 PLC 后，这两个默认任务绑定才允许随该 PLC runtime 启动。
- 设备只允许按稳定 `PlcCode` 复用；同名设备已属于其它代码时必须失败关闭，禁止按可变名称认领或覆盖。
- 首次播种事务必须完整写入该版本要求的设备、IO 和任务绑定；已存在任意一条 IO 不能成为跳过其它缺失 IO 的理由。播种成功后记录完成版本，后续任何普通启动都不得再次播种。
- 插件 Schema 升级只能通过显式迁移逐项增加该版本必需结构或数据，并保留现场修改的 IP、端口、PLC 地址、地址数量、名称、备注、启用状态和任务选择；禁止把升级伪装成重新播种。
- 生产启动禁止自动执行 `ResetBeforeImport`、清空重建或其它 destructive reset。
- 任何新增业务任务都必须先完成对应业务裁决和接口契约；当前 R100 设备工况只引用 `BR-CURRENT-010`，不得提前播种。

#### PLC-TASK-001：AP/CP 必须具有三个独立业务任务

- 当前 AP 和 CP 的每台适用 PLC 分别运行 MG1 弹夹任务和 MG2 弹夹任务。
- MG1、MG2 必须可以分别绑定、启用、停用、诊断和运行；任一槽位失败不得改变另一槽位结果。
- PLC 连接、连接健康、通用心跳、信号交互、握手、必要写入和请求排队属于 Host 通用能力，不得伪装成第四个工序业务任务。
- R100 当前按 `BR-CURRENT-010` 冻结，不得实现、播种或上报未批准的第三任务链；未来只有用户单独确认后才能转为正式业务任务。

#### PLC-READ-001：不同数据必须按业务需要读取

- 实际产量、模切速度等单点数据必须由 Host 周期性批量读取，并整体发布到当前 PLC 的 buffer，供通用采集、UI 和诊断使用；该周期快照不得与另一批次按需读取的条码拼接成业务快照。
- MG1 任务必须通过统一 PLC 请求协调器按需原子读取 MG1 弹夹码、收料片数和模切速度；MG2 任务必须独立按需原子读取 MG2 弹夹码、收料片数和模切速度。每次请求只包含当前任务的条码和其完整业务必需信号，禁止读取另一槽位条码，也禁止周期任务无条件读取两个槽位的弹夹码。
- 弹夹任务必须直接获得本次完整原子读取的成功或失败结果；条码、数量、速度、质量和采集 UTC 必须由同一个真实 `Generation/BatchId` 一次发布，禁止用无法判断来源的空字符串、全零 buffer 值或旧周期值补齐本批。
- 未批准的 R100 设备工况不得进入读取计划；当前冻结说明见 `BR-CURRENT-010`，本文不保留地址、类型或值域。
- PLC 地址允许具有配置权限的本地 `Admin` 现场修改；修改后仍必须满足对应数据类型和解码长度要求。
- IO 保存、任务绑定与 runtime 构建必须共用 SDK 的同一类型/word 长度校验器：`Bool/Int16/UInt16` 每值 1 word，`Int32/UInt32/DWord/Float` 每值 2 words，`Ascii` 只接受正长度；连续映射的总 word 数必须按单值宽度对齐。任一映射无效时必须在保存或绑定边界失败关闭，运行期只能跳过该映射并隔离依赖它的 `TaskKey`，不得拖停 PLC 基础 runtime 或其它有效任务。
- “单点读数据”或“连续读数据”只描述一项数据占用的 PLC 地址形态，不自动决定读取频率；读取时机必须由周期批量读取任务或对应业务任务明确负责。
- 按需读取成功后必须把本次完整结果和值质量原子同步到 buffer；业务判断只使用本次调用返回的同一不可变快照，不得重新读取实时 buffer 或混入周期快照。

#### PLC-BLOCK-001：近地址必须合并，远地址必须拆块

- 同一地址前缀下的单点读取必须按最小覆盖区间合并，默认单块最大长度为 100 words；插件可以声明更小的安全上限。
- `D101`、`D103`、`D108` 必须合并为从 `D101` 开始、长度 8 words 的一次读取，禁止无依据扩展为固定 `D100 × 10`。
- 当最小覆盖区间超过当前最大块长度时必须拆块；`D101`、`D201`、`D301` 在默认 100 words 上限下必须拆分。
- 不同地址前缀、无法可靠解析的地址或 PLC 协议不允许跨区读取的地址必须分别成块。
- 远地址拆块后仍通过同一 PLC 请求队列依次执行；“拆成多个任务”不等于为同一 PLC 打开多个真实连接。

#### PLC-SCHED-001：同一 PLC 必须按读取优先级排队

- 同一 PLC 的所有读写请求必须进入一个统一调度队列，禁止各任务绕过队列直接争用协议对象。
- 第一优先级是信号交互、握手、必要写入和维持协议健康所需的请求。
- 第二优先级是当前已经批准的插件业务任务读取；当前 AP/CP 为 MG1、MG2。
- 第三优先级是实际产量、模切速度等周期批量读取。
- 同一优先级必须按入队顺序 FIFO 执行；不得用任务名、模块名或调用线程改变同级顺序。
- 每个请求的等待老化窗口必须使用当前扫描间隔并限制在 500ms—5s；每等待满一个窗口提升一级，直至最高优先级，禁止因为高优先级请求持续到达而永久读不到。
- 优先级只决定同一 PLC 下一条请求先执行谁，不改变“同一 PLC 单连接串行、不同 PLC 并行”的规则。

#### PLC-ONLINE-001：PLC 在线与任务数据质量必须分开

- PLC 在线只说明当前通讯连接仍可工作，不代表所有业务点位、批次或任务均健康。
- 只有 `TransportDisconnected`，即异常链中存在明确 `SocketException` 的真实传输断开，才允许把 PLC 标记为断联并进入重连；超时、协议拒绝、坏报文、配置错误、裸 `IOException` 和普通任务故障不得按累计次数升级成断联。
- 某个地址、block、周期读取 owner 或任务必需信号失败时，只能把对应信号和依赖任务标记为不可用；其它成功任务和其它 PLC 必须继续。
- 任一其它 block 成功可以证明连接仍有响应，但不得把本次失败的任务重新标记为健康。
- 连接状态、信号质量和任务运行状态必须分别显示和记录，禁止用一个“在线”状态掩盖局部读取失败。

#### PLC-NAME-001：任务名称必须直接说明职责

- 通用 PLC 类、日志和诊断名称必须直接区分信号交互、周期批量读取和当前 MG1/MG2 弹夹任务，禁止继续用一个含糊的 `Scan` 覆盖不同链路；未来任务只有批准后才进入命名规则。
- Host 新 runtime 必须实例化 `PlcSignalInteractionTask` 和 `PlcPeriodicBatchReadTask`，中文名称分别为“PLC 信号交互任务”和“PLC 周期批量读取任务”。
- Host API 2.0.x 为二进制兼容保留的 `PlcIoScanTask`、`PlcDataReadScanTask` 只能作为委托给新实现的薄包装，不得注册为第二套生产任务或形成调度旁路；删除它们必须等 Host API 2.1.0 的显式退出批次。
- 类名调整不得改变任何已持久化 `TaskKey`、公共接口或兼容契约；诊断与 UI 必须始终使用明确职责名称。

#### PLC-ID-001：PLC 只能有一个稳定业务标识

- `PlcCode` 必须是 PLC 唯一、稳定且永久不可变的业务标识。
- 插件设备解析、运行上下文归属、任务业务身份、生产事实、日志和后续补传追溯必须使用 `PlcCode`。
- `DeviceName` 是允许现场修改的展示名称及 MES 所需字段，禁止用它查找插件设备、关联历史事实或充当业务主键。
- 旧产能缓冲中的历史 PLC 身份只允许先精确匹配当前 `PlcCode`，再匹配持久化别名表中唯一且未被其它 `PlcCode` 复用的已验证历史别名；任一当前 `DeviceName` 即使已出现在别名表中也不得据此认领为稳定代码。权威 PLC 配置读取失败时必须保留原记录、不领取、不上传；其余无法唯一解析代码、真实名称或 AP/CP 工序的旧缓存不得猜测映射，只能保留原 `PlcName` 身份按 Cloud v1 上传，并在 Cloud 明确 ACK 后删除。补传每轮最多领取三批，必须以原始 `RecordId` 游标跨轮继续，不得取消单轮工作上限。
- 当前 PLC 配置或唯一已验证历史别名能够同时确认稳定 `PlcCode`、当前真实 `DeviceName` 和 AP/CP 工序时，产能缓存必须发送 Cloud v2；无法确认这些 v2 事实的旧缓存按原身份发送 v1。v1/v2 都必须保持同一时槽快照幂等，ACK 丢失后的重试不得重复增加 Cloud 产能。
- `NetworkDeviceId` 只允许作为本地数据库主键、外键和进程内实现细节；它不是第二个 PLC 业务身份，不得对外形成另一套匹配规则。

#### PLC-RUNTIME-001：每台已启用 PLC 必须拥有独立 runtime

- Host 必须遍历所有“已启用且设备类型为 PLC”的设备，并为每台 PLC 创建独立 runtime。
- 不同 PLC 的初始化、连接和任务循环必须并行且相互隔离；一台 PLC 连接、读取或任务失败不得停止其它 PLC。
- 同一 PLC 内可以同时运行通用任务和当前目标插件的多个业务任务，但必须共用当前 PLC 的唯一通讯连接。
- 同一 PLC 的真实读写报文必须通过统一请求队列串行发送；禁止为了表面并行而默认为同一 PLC 建立多个未验证连接。
- 未启用 PLC 必须保留配置和任务绑定，但不得连接 PLC、启动该设备 runtime 或伪造在线状态。

#### PLC-BIND-001：一个 Shell 必须恰好只有一个工序任务工厂

- 一个启动项对应一个 `ClientCode`；其 Shell 进程必须恰好绑定该 `ClientCode` 设备插件的任务工厂，并由该工厂声明可供插件内每台 PLC 动态选择的任务。
- Host 必须按每台 PLC 保存的启用状态、任务绑定、设备型号和必需 IO，分别决定本 PLC 启动哪些任务。
- 同一套通用 Host 必须允许不同 PLC 启用不同任务组合，禁止把 AP/CP 任务写死到 Host 全局分支。
- 目标插件任务工厂缺失、重复或身份不一致时，必须跳过该插件业务任务并形成明确诊断；已经能够安全启动的 PLC 基础任务可以继续运行。
- 工厂异常、插件缺失或任务绑定问题不得阻断 Shell 进入可诊断、可修配置的 UI。

#### PLC-FACTORY-001：一个任务工厂必须提供多个可动态绑定任务

- 目标插件任务工厂只声明该插件真实拥有的任务，并允许插件内每台 PLC 保存不同启用组合；框架不得预设所有插件都具有 MG1、MG2、设备工况或固定任务数量。
- 同一候选任务可以绑定到多台适用 PLC，不同 PLC 的选择和运行结果必须隔离。
- 目标插件工厂缺失、重复或身份不一致时，只能跳过插件业务任务并形成明确诊断；PLC 基础连接、信号交互和修复 UI 必须继续。
- 禁止把一个插件的动态任务绑定实现为多个互相竞争的业务工厂，也不得装入其它插件的工厂补缺。

#### PLC-BIND-002：SQLite 必须是运行时任务启用状态的唯一来源

- 每台 PLC、每个 `TaskKey` 的启用状态必须以正式 SQLite 绑定记录为唯一运行时事实；业务身份按 `PlcCode + TaskKey` 解释，`NetworkDeviceId` 只作 SQLite 内部主外键和本地持久化行定位字段，不能作为业务身份或归属回退；`DeviceName` 只作展示。
- `DefaultEnabled` 和插件初始值只允许在私有数据库首次创建时播种一次；Schema 升级只能由显式版本迁移新增确有需要的绑定，且不得覆盖已保存选择。全局 Host 配置不得成为插件任务默认值。
- 运行时、任务绑定页面和重启恢复必须读取同一条 SQLite 记录；缺行时关闭对应任务并显示“绑定缺失”，禁止回退为默认启用。

#### PLC-BIND-003：业务任务必须在 PLC 已连接且自身配置有效后启动

- 业务任务只有同时满足“SQLite 已启用、PLC 型号支持、必需 IO 完整且类型/长度有效、当前 PLC TCP 已连接”时才能启动。
- 首次连接失败时只运行基础连接和退避重试；业务任务保持“等待 PLC”。离线期间允许可靠保存绑定，不能伪装成运行中或保存失败。
- 连接成功后按 SQLite 当前状态逐任务校验和启动；一个任务配置无效只能阻止该任务。

#### PLC-BIND-004：绑定保存和运行时应用必须具有完整事务语义

- 单台 PLC 的一次绑定保存必须在同一命令中完成候选、型号、必需 IO、数据类型和地址长度校验，并在一个 SQLite 事务中保存涉及行、计算相对原绑定的任务增量。
- SQLite 提交后只能启动或停止发生变化的任务；界面只有在 SQLite 与任务增量均成功后才能显示成功。
- 运行时应用失败时必须恢复提交前的 SQLite 绑定和任务组合；PLC 离线而任务进入“等待 PLC”属于成功应用，不得回滚。
- 绑定事务必须与同一 PLC 的硬件、端口、协议帧、共享 IO 保存及插件标准点位重置共用一个配置变更门；硬件命令必须在读取权威快照或写入 IO 映射前进入该门，并持有至设备停机或重载结束，绑定事务的原状态快照、提交、运行时应用和双向补偿期间也不得穿插另一项运行配置变更。
- 整页硬件保存必须由门内权威快照生成显式更新、删除和 IO 变更计划：只写入实际变化的行，未变化 PLC 和未变化 IO 不得被全量提交重写；因此每个实际写入的 PLC 都已持有自身配置变更门，而未受影响 PLC 不得被其它设备的慢重载阻塞。

#### PLC-BIND-005：启停一个任务只能改变该任务

- 启用只创建并启动目标任务；停用只取消并等待目标任务安全退出。禁止重建 PLC service、连接、buffer、其它任务或其它 PLC runtime。
- 单任务启动、停止或初始化失败只进入本任务诊断；只有共享 PLC service、请求调度器或真实连接无法安全工作时，才允许影响当前 PLC 的全部业务任务。

#### PLC-ISOLATION-001：一个任务失败不得停止其它有效任务

- 某个候选任务缺少必需 IO、地址无效、数据类型不匹配或初始化失败时，只能阻止该任务。
- 同一 PLC 的其它有效业务任务、通用连接任务和读取任务必须继续启动和运行。
- 每个失败任务必须输出 `PlcCode`、任务 Key、缺失或错误信号及修复要求，禁止只把整台 PLC 标成一个无法定位的故障。
- 只有当前 PLC 的连接、协议服务或共享请求调度器无法安全工作时，才允许停止该 PLC 的全部任务。

#### PLC-BIND-006：任务停用必须立即生效并保留业务检查点

- 每个支持检查点的任务必须以 `ClientCode + PlcCode + TaskKey` 独立保存槽位、弹夹、未完成数据、业务时间和恢复状态，并以单调 revision 提供并发确认门；`ModuleId`、profile 或名称不得参与归属回退。当前 MG1、MG2 禁止互相覆盖，未批准的新任务不得提前制造检查点或待上传事实。
- 本地 `Admin` 确认停用后必须先停止目标任务产生新状态，再原子保存该任务检查点；检查点未持久化时，绑定保存必须失败并恢复原 SQLite 行和原任务组合，禁止把失败显示成已停用。断联、重连和周期读取故障暂停必须复用原任务实例且不得创建恢复检查点。
- 进程关闭顺序固定为“停止任务并分别保存检查点 → 最终保存生产上下文”；检查点或最终上下文保存失败必须显式报告，禁止静默关闭。重新启用或进程重启后必须等待第一份成功且新鲜的本任务快照，失败质量、过期或混批快照不得推进恢复。
- 恢复一致性与终止审计中的“现场读值”固定指同一原子成功新鲜快照内的弹夹码、数量、速度和采集 UTC，其中 revision 的业务比较键只包含弹夹码、数量和速度，采集 UTC 是该版三项读值的关联时间，不单独触发变更。三项任一变化，或旧检查点缺少数量、速度、采集时间中的任一项时，必须用该份完整观测更新检查点并递增 revision；已有完整观测且三项完全相同时，后续仅采集 UTC 推进的快照不得覆盖已落盘观测、重复落盘或产生 revision 抖动。
- AP、CP 在等待人工确认时必须各自以大小写不敏感的 `PlcCode + TaskKey` 隔离运行期确认租约，并绑定当前检查点 revision、最近一次成功新鲜快照时间和现有配置的新鲜窗口。确认只有在租约存在、revision 一致且仍在窗口内时才允许执行；否则必须返回 `ObservationNotEligible + RecoveryObservationUnavailable`，且不得修改检查点、写入终止审计或产生任何业务输出。
- 断联、快照缺失/混批/失败/过期、解码异常和任务停止必须先撤销对应租约。首次失效必须清空当前可确认观测、推进一次 revision 并保存稳定原因码；重复失效不得持续落盘或抖动 revision。即使失效状态持久化失败，内存租约仍保持撤销；插件重启后默认没有租约。下一份成功新鲜快照必须重新保存完整观测并推进 revision，即使弹夹码、数量和速度与失效前相同；只有保存成功后才能重新签发租约。连续健康且三项不变时只刷新运行期新鲜时间，不得重复落盘或推进 revision。
- 首份新鲜快照与检查点同码时必须续跑原弹夹，不新建、不完工、不重复入队，并将本次接受的数量、速度和采集时间原子同步到活动单元、生产上下文和检查点；异码或空码时必须保持旧未完成件、计数和业务输出不动，并进入本地人工确认。
- 只有当前已登录且具备恢复权限的本地 `Admin` 可以处理恢复：现场重新变回同码时确认恢复原检查点；异码或空码时只能审计终止旧未完成件，并保存操作人、UTC 时间、旧状态以及最新现场弹夹码、数量、速度和采集时间，不得生成完工、MES/Cloud 数据或产量。完整现场观测尚未建立时必须以 `RecoveryObservationMissing` 失败关闭；异码审计终止后必须等待下一份新鲜快照才能创建新弹夹，空码继续等待。
- 任务绑定页面必须显示 SDK 公共恢复快照提供的检查点弹夹、现场弹夹码、恢复状态、检查点/读值时间和稳定原因码，并只在需要人工确认时显示操作入口。数量、速度保留在插件私有检查点和终止审计中，不扩展 SDK 公共恢复快照或单独投影到页面；二者是审计新鲜度的并发输入，不是本地 `Admin` 的业务决策或审批字段，本地 `Admin` 只核对页面可见的弹夹码和恢复状态。弹夹码、数量或速度任一变化都必须推进页面携带的 revision；旧 revision 冲突后，页面必须刷新取得绑定最新私有审计值的新 revision，本地 `Admin` 重新核对可见字段后才能提交，确认结果原子引用该 revision 对应的完整审计观测。若数量或速度在刷新与提交之间再次变化，命令必须再次冲突，禁止用旧 revision 确认；仅采集 UTC 推进而三项未变时，确认仍针对原已落盘观测。

#### PLC-TASKSTATE-001：任务绑定页面必须展示每个任务的真实运行状态

- 进程内运行状态必须以大小写不敏感的 `PlcCode + TaskKey` 独立维护，只允许 `WaitingForRuntime`、`WaitingForConnection`、`Starting`、`Running`、`Stopping`、`Faulted`；不得使用 `DeviceName`、数据库行号或新增 SQLite 表作为状态身份。
- 页面展示优先级固定为绑定缺失、已禁用、PLC 型号或 IO 配置无效、等待 runtime/连接、实际任务运行状态；PLC 在线但任务配置错误不得显示运行中，PLC 未连接但任务有效不得显示配置错误。
- 每项必须显示状态变更 UTC 时间，以及最近一次成功完成任务启动/恢复握手并进入 `Running` 的 UTC 时间；首次成功前后者为空，故障、停止和等待连接时保留，重连后再次成功进入 `Running` 时推进。页面必须明确标注“最近成功启动/恢复”，禁止冒充 PLC 数据读取成功、业务循环成功或生产完工时间。故障只显示稳定错误码、安全文案和异常类型，禁止显示原始异常消息。状态投影必须进入现有任务绑定页面，页面激活时订阅、停用时解除订阅，并只更新对应 `PlcCode + TaskKey` 行，禁止为状态变化循环重查 SQLite。
- 断联暂停后必须保留任务实例并进入 `WaitingForConnection`，重连后由同一实例重新经过 `Starting → Running`；主动停用或 runtime 安全释放后清除快照，未安全释放的隔离 runtime 必须保留 `Faulted` 快照。
- Host 任务计划必须按候选任务声明的 `Read` 必需信号及其已解析 IO 类别，只有信号由周期读取实际负责的单点读/连续读数据类别时，才显式标记对应 `TaskKey` 依赖周期读取；交互读和其它非周期读取 owner 不得误标。禁止按任务名猜测或给未声明任务提供默认旁路。周期读取非 transport 故障或意外退出时，只暂停当前 PLC 中仍在运行且依赖周期读取的任务；写-only 任务和其它 PLC 不受影响。
- 周期读取故障暂停成功后，目标任务固定为 `Faulted/PeriodicReadFault`；停止超时或停止失败必须保留 `TaskStopTimeout`/`TaskStopFailed`，不得被通用周期读取错误覆盖。该故障不得断开 TCP、释放 PLC service、重建 buffer、任务实例或生产上下文，也不得忙循环自动重启；只有后续真实 transport 断联后的重连，或受控 runtime 重载并成功启动周期读取后，读依赖任务才允许再次进入 `Starting → Running`。

#### PLC-CONN-001：McpX TCP 建连结果必须是当前 MC PLC 的初始连接门禁

- 当前 MC 客户端固定使用 `McpX 0.6.0` TCP，不启用 UDP。`TcpClient.ConnectAsync` 成功即表示本次初始连接成功，失败或超时按连接失败处理。
- 建连成功即可启动符合条件的任务，禁止要求连续读取业务点位或虚假只读点位才视为在线；纯写配置也不得被附加读探针。
- 未批准的业务信号不得参与连接、重连或写入许可。

#### PLC-CONN-002：首次连接门禁和运行中断联恢复必须分开

- 首次连接失败时不创建业务任务实例；连接成功后按当前绑定逐项启动。
- 已启动后发生明确 Socket/TCP 关闭时，保留任务实例、上下文和检查点并进入断联暂停；重连成功恢复原实例，禁止通过销毁、重建全部任务冒充恢复。
- 重连期间不得推进弹夹、空码计数、任何业务完成事实或写入确认；一台 PLC 的断联不得改变其它 PLC。

#### PLC-ERROR-001：连接错误和任务操作错误必须按真实原因分类

- 运行期异常必须穿透包装异常和 `AggregateException` 分类；异常链中存在 `SocketException` 时固定为 `TransportDisconnected` 并具有最高优先级，只有这一类可以标记断联、释放连接并进入重连。
- `TimeoutException` 为 `Timeout`，`McProtocolException` 为 `ProtocolRejected`，`RecivePacketException`/`InvalidDataException` 为 `InvalidResponse`，`DeviceAddressException`/`FormatException`/`ArgumentException`/`NotSupportedException` 为 `ConfigurationInvalid`；裸 `IOException`、未知异常和非调用方取消统一为 `TaskFault`。
- 非 transport 读写失败只发布失败质量并保留 TCP 状态和待写意图；周期读取非 transport 故障还必须按 `PLC-TASKSTATE-001` 只暂停真实读依赖任务。普通初始化或任务异常不得无条件调用设备级 `MarkDisconnected`，只有 runtime 自身无法安全继续时才标记 `Faulted`。调用方取消原样传播，PLC service 隔离继续走独立隔离路径。
- 日志和 UI 只允许真实操作、地址、长度、`PlcCode`、`TaskKey`、稳定原因码、安全文案和异常类型，禁止显示原始异常消息。

#### PLC-BUFFER-001：批读结果必须作为完整快照发布

- Host 必须先在本轮采集中汇总完整信号集合，再通过原子批次发布接口一次提交；同一快照中的 `Generation`、`BatchId`、UTC 采集时间和信号集合必须一致，禁止逐信号暴露半份新数据。
- 业务只允许按本轮声明的必需信号集合捕获一次不可变快照；缺少信号、混合批次、发布能力缺失或捕获失败必须失败关闭。快照对外数据必须深复制，后续实时 Buffer 发布不得改变已捕获内容。
- 读取失败的信号可以进入快照，但只能携带类型默认值和 `ReadSucceeded=false`；最后成功值只保留在 UI/诊断维度，不得进入业务快照。手工读取或单信号展示更新不得伪造新的成功批次。
- 单次业务循环的质量判断、强类型解码、业务值和时间必须全部来自同一快照；捕获后禁止重新读取实时 Buffer。

#### PLC-QUALITY-001：读取失败不得伪造 0 或空值

- block 或信号读取失败时必须发布类型默认值、失败质量、本批次和失败时间；不得刷新最后成功时间，也不得把默认值解释为 PLC 真实返回的 0 或空字符串。
- 原规则中“保留旧成功值供业务继续读取”和“block 失败后允许单点重读”的执行口径已由 `PLC-READ-FAIL-001` 取代：block 失败禁止单信号降级，last-good 只可诊断。
- SDK 强类型访问器遇到缺失信号或 `ReadSucceeded=false` 时必须返回不可用或受控失败，禁止回退 `GetReadValue`、`TryGetReadWords` 等实时 Buffer 路径。
- 任一业务必需信号缺失、混批、失败或过期时，本轮必须标记不可用并停止解码、状态推进、入队和完工；无关信号失败不得扩大为其它任务故障。

#### PLC-READ-FAIL-001：批量读取失败必须返回失败质量，禁止单信号降级

- block 读取失败后禁止拆成逐信号请求兜底；受影响信号一次发布类型默认值、`ReadSucceeded=false`、本批次和失败时间。
- 最后成功值只保留用于 UI/诊断，禁止作为本轮业务输入或刷新最后成功时间。
- 弹夹码失败不得累计空码，不得新增、切换、完成或移除弹夹，并重置连续空码确认计数；其它数据失败只暂停依赖该数据的任务。

#### PLC-CLIP-001：弹夹判断必须使用本次成功条码和新鲜批读数据

- MG1 任务只能处理 MG1 弹夹码，MG2 任务只能处理 MG2 弹夹码；每轮只捕获一次同时包含本槽位条码、收料片数和模切速度的原子快照，三项值及 UTC 时间必须来自同一 `Generation/BatchId`。
- `SnapshotFreshnessWindowMs` 默认 3000ms，有效值不得小于任务扫描周期。快照时间晚于当前 UTC、超过新鲜窗口、采集时间不递增、Generation 回退或同 Generation 对应不同 BatchId 时必须失败关闭。
- 缺信号、混批、任一信号 `ReadSucceeded=false`、任务重建或连接故障时必须 `MarkUnavailable`，清空连续空码和空转移候选；不得解码默认值、推进弹夹状态、入队或触发完工。
- 新成功 Generation 与上次成功 Generation 的采集时间间隔超过新鲜窗口时，必须先清空旧确认，再把当前批作为新序列的第一个批次；同一 Generation 超过窗口后重复读取也必须清空旧确认。

#### PLC-CLIP-002：空弹夹必须连续三次读取成功后确认

- 弹夹由有值变为空字符串时，只有三个不同、连续、质量成功且处于新鲜窗口内的 Generation 均为空，才能以第三个快照的 UTC 采集时间确认清空并进入完工处理。
- 同一成功 Generation 被任务循环重复调用只能计算一次；同 Generation 不同 BatchId、Generation 回退、时间不递增或未来时间必须失败关闭。
- 任一次读取失败、缺信号、混批、过期、断联或任务重建都不得计作空值，并必须清空连续空码计数；后续从新的成功 Generation 重新计数。
- 真实读取成功且得到非空弹夹码时必须立即清除未完成的空码确认；MG1、MG2 分别维护自己的当前弹夹和计数，禁止相互复用。

#### PLC-WRITE-FAIL-001：写入失败必须保留原写入意图

- 写入失败不得清零、覆盖或消费写 buffer；原待写值和请求上下文保持不变，不得记录为已写入、已握手、已确认或上传成功。
- 除非底层同时明确报告 Socket/TCP 断开，否则只标记受影响任务写入失败，不改变 PLC 连接状态；后续受控重试继续使用原意图。
- 日志必须包含 `PlcCode`、任务、地址、长度、失败类型和脱敏原因。

#### PLC-STATUS-001：设备状态必须由独立任务产生并且只上传 Cloud

- 本编号只为保留稳定引用；当前冻结事实的唯一说明是 `BR-CURRENT-010`，本文不复制 R100 地址、值域、映射、任务、频率、断线或上传设计。
- 在取得正式 PLC 资料并完成用户裁决前，不得把设备工况登记为当前规则、已实现能力、生产 Schema 或验收结论。
- 未来若批准实施，再按裁决结果更新本稳定编号、技术契约、代码和受影响测试；不得从旧候选正文恢复默认方案。

## 6. 业务复审场景

1. **同机多插件**：同一上位机安装设备插件 A、设备插件 B 和其它工序插件；Launcher 显示三个独立启动项并允许同时运行。
2. **同 ClientCode 防重**：设备 A 对应的 `ClientCode` 已运行时，再次点击同一张设备 A 卡片必须阻止；拥有其它 `ClientCode` 的设备 B 和其它设备插件不受影响。
3. **插件内多 PLC**：某插件包含 12 个 PLC 时，客户端保留 12 个 PLC 的真实配置、状态和数据归属，不把它们变成 12 个插件或 12 台上位机。
4. **故障隔离**：一个插件配置错误、PLC 断连或 Cloud/MES 通道故障时，只影响相应插件、PLC 或通道，并保持可诊断 UI。
5. **真实数据**：无真实完成事实时生产页为空；入队、缓存、补传或外部上传结果都不生成生产记录。
6. **新增插件**：新增任意现场设备必须具有独立插件包、独立发布版本链、独立业务文档、独立 `ClientCode`、独立私有数据库和 `plugins/{ClientCode}` 目录，再通过 Cloud 标准链到达 Launcher；通用 Launcher/Shell/Host/SDK 不增加该设备名称判断。
7. **完整离线包**：在未预装 .NET/SDK 且安装期间断网的目标 Windows 上，安装包仍能完成安装并打开 Launcher/Shell；若任一 `.deps.json`、`.runtimeconfig.json`、runtime、native、DLL、Avalonia/Skia/Velopack、语言资源、页面路由、首次播种定义、配置、签名或恢复材料缺失，则 Cloud 生成或安装预检必须提前失败，不能安装后再报缺文件。
8. **宿主、插件与凭据隔离**：`host.db` 只出现宿主公共状态；设备 A、设备 B 的业务库、PLC、MES、日志和缓存分别位于各自 `plugins/{ClientCode}` 边界，凭据原文按 `ClientCode` 位于实际 Launcher Windows 账户 Credential Manager。删除或损坏设备 A 私有数据不得改变设备 B，任一 secret 不得出现在 `host.db`、插件普通文件/数据库、运行时 Binding、日志或审计摘要。
9. **首次播种一次**：一个新 `ClientCode` 私有数据库首次创建时播种一次，随后连续重启、断网重启和 Launcher 重开均不再次播种、不覆盖现场 IP、端口、任务选择或 MES 配置；版本升级只运行显式迁移。
10. **PLC 缓存双杀与失败保护**：配置写入按“写前失效并提升版本 → 数据库提交并重载 → 写后再次失效并加载已提交值”执行，写入前启动的旧并发读取不得回填旧版本。缓存 miss 后数据库读取失败时，插件返回 `Unavailable` 且不发送权威空清单；Cloud 保留上次 PLC 总览。只有具有配置权限的本地 `Admin` 明确保存空 PLC 配置并产生新 revision，才允许权威清空。
11. **Cloud/MES 双链路**：同一完成事实分别进入 Cloud、MES 独立出口；任一身份、心跳、上传、retry、fallback 或 deadletter 故障不得伪装成另一通道结果，也不得阻止本地完成事实和另一通道。
12. **多设备 Binding 激活**：同一签名安装信封包含设备 A、设备 B 时，Installer 将两者原凭证分别作为 Pending 项导入 Credential Manager，运行时 Binding 不含原文；完整文件组原子安装成功只删除 staging 明文副本，Credential Manager 中每项保留到所属设备激活成功或 Pending 过期。设备 A Ready 只激活设备 A；设备 B 未启动、失败或 Pending 过期不回滚设备 A，也不撤销设备 B 的旧有效会话。
13. **旧凭据安全迁移**：发现旧明文会话时，Launcher 必须先完成更新恢复，再迁移 `host.db` 公共状态，然后按 `ClientCode` 写入并回读 Credential Manager、提交脱敏引用，最后才删除明文源；中途失败进入可恢复诊断，不产生空凭据、假完成标记或密钥日志。
