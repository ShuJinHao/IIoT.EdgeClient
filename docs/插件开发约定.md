# 插件开发约定

本文档是 EdgeClient 插件开发的固定约定。宿主可以复杂，插件必须保持简单，并且只能遵守一套入口规范。

## 业务边界红线

- 一个工序插件就是一个完整业务承载单元。匀浆、模切、叠片等工序业务必须放在各自的 `src/Modules/IIoT.Edge.Module.<Process>/` 下闭环实现。
- `IIoT.Edge.Module.Homogenization` 是当前标准参考插件；新增工序只能参考它的接入形态，不能把匀浆业务拆到宿主，也不能把新工序业务写进 Host、Application、Runtime、Infrastructure 或 Shared。
- 插件内部可以自包含运行任务、PLC/MES/Cloud 适配、payload、硬件模板、参数声明和 Presentation 页面；这些属于插件边界，不应被误判为需要拆出插件。
- 宿主只提供通用契约、运行时基础设施、组合根、导航注册和共享 UI 能力；宿主不得出现针对某个具体工序的业务分支。
- 任何要拆插件程序集、迁移插件业务、改 MES payload、改 PLC 交互、改 Runtime task 行为的方案，都必须先单独确认。
- `IIoT.Edge.Runtime` 当前保留为宿主运行基础设施和插件运行 SDK，不作为本约定的删除目标。

## 模块入口

- 插件入口类型只能实现 `IEdgeProcessModule`。
- 插件只在 `Configure(IEdgeProcessModuleBuilder builder)` 中向宿主声明能力。
- 模块 ID、工序类型、显示名、服务注册、`CellData` 注册、运行时任务工厂、上传器、UI 注册都通过 `IEdgeProcessModuleBuilder` 完成。
- 不允许新增旧接口、适配器、过渡层或多套入口分支，除非用户明确要求。

## 开发阶段代码质量硬规则

当前项目仍处于开发阶段，不做历史兼容维护。发现旧接口、旧枚举、旧 ViewModel、旧资源 key、过渡 adapter 或双轨调用方式时，必须直接清理，不允许用 `Obsolete`、转发方法或兼容分支继续保留包袱。

- 同一能力只能保留一套入口、一套调用方式、一套缓存策略。
- 通用能力优先使用泛型、接口抽象、基类模板、装饰器/AOP 式横切封装，禁止把日志、缓存、重试、权限、诊断等横切逻辑复制到业务任务里。
- 复杂状态机、公共抽象、插件入口、参数枚举和关键业务方法必须有必要的中文注释；注释只解释业务意图和调试线索，不写无意义说明。
- 新增或修改的现场可见日志、状态、诊断、校验文案必须使用中文。

## 共享 UI 资源规则

第三方 WPF UI 框架依赖必须由 `IIoT.Edge.UI.Shared` 统一承载。Launcher、Shell、Presentation 页面和插件页面如需使用 MaterialDesign 控件、图标、主题或附加属性，必须通过共享 UI 项目获得引用，不允许在业务项目或启动项目重复添加 `MaterialDesignThemes`。

- 字体、图标、图片等共享 UI 资源只能放在 `IIoT.Edge.UI.Shared/Assets/` 下，由共享 UI 项目统一声明。
- 不允许把 NuGet 包自动带入的 `Resources/Noto`、`Resources/Roboto` 或其他 content 字体复制到各项目。
- `MaterialDesignThemes` 引用必须排除 `contentFiles`，避免第三方字体挂到多个项目树或发布输出。
- 新增 WPF 项目需要通用 UI 能力时，优先引用 `IIoT.Edge.UI.Shared`；只有共享 UI 无法承载的新基础设施能力，才允许讨论新增直接包引用。

## 客户端/云端分离开发硬规则

当前阶段客户端和云端分开开发。EdgeClient 默认只处理客户端通用框架、插件接入、运行时任务、上传抽象、本地补偿、诊断和启动项配置；不得因为 Cloud 上传、端到端闭环、审计建议、Assumptions 或测试便利去修改 `IIoT.CloudPlatform`。

- 客户端任务中可以先实现通用 Cloud channel、payload mapper、retry/fallback/deadletter 接入，但不能自行补云端 endpoint、事件、worker、SQL、迁移或查询框架。
- 云端上传对齐必须作为后续单独任务处理，并且需要用户明确授权当前任务允许修改云端。
- 新增工序时，插件按匀浆模块的结构方式开发，业务模型留在插件内；宿主只通过 `IEdgeProcessModuleBuilder`、模块注册和 launcher profile 识别新工序。
- 如果用户只要求客户端开发，最终 diff 不允许出现 `IIoT.CloudPlatform` 路径；发现云端已有其他改动时，只记录状态，不回退、不覆盖、不顺手修。

## 插件接入宿主流程

新增工序只接入客户端时，默认不修改云端项目，也不把客户端需求扩展成云边联动改造。若确实需要云端接口、云端表或云端查询支持，必须作为单独任务先与用户确认。

插件接入宿主按以下顺序执行：

1. 在 `src/Modules/IIoT.Edge.Module.<Process>` 下建立插件项目，插件入口继承 `EdgeProcessModuleBase<TCellData>` 或直接实现 `IEdgeProcessModule`。
2. 在插件入口中固定声明 `ModuleId`、`ProcessType`、`DisplayName`、Cloud 上传模式，以及需要时的 MES 上传模式。
3. 通过 `IEdgeProcessModuleBuilder` 注册插件能力：`CellData`、运行时工厂、Cloud/MES 上传器、PLC 信号 profile、硬件模板、开发样本、标准页面和必要的插件配置。
4. 运行任务由插件自己的 `IStationRuntimeFactory` 创建，任务只依赖宿主提供的 PLC buffer、强类型 Context、DataPipeline、日志、`IIoT.Edge.Runtime` 强类型 IO accessor 和共享基类。
5. 工序菜单、页面和面板通过插件自己的导航注册扩展加入宿主，`ViewId` 必须以模块 ID 开头，不允许注册 `Core.*`。
6. 启动器不为某个工序单独写 XAML。启动项来自 `launcher.profiles.json`，该文件由 `scripts/edge-runtime.publish.json` 和生成脚本维护。

插件接入宿主时禁止以下做法：

- 禁止在宿主启动、导航、DataPipeline、PLC runtime 中硬编码某个工序的业务分支。
- 禁止绕过 `IEdgeProcessModuleBuilder` 直接写宿主注册表或静态全局表。
- 禁止把插件 payload、PLC 信号、Context、任务状态机、Cloud/MES 字段映射上提到宿主或共享层。
- 禁止插件直接 `builder.Services.AddSingleton<IModuleHardwareProfileProvider, ...>` 或 `AddSingleton<IDevelopmentSampleContributor, ...>`；必须使用 `RegisterPlcSignalProfile`、`RegisterHardwareProfile`、`RegisterDevelopmentSample`。
- 禁止在客户端插件任务中修改云端项目、云端接口、云端表结构或云端查询。

## 文件结构

- 一个插件代表一个工序，例如匀浆或后续新增工序。
- 每个插件只保留必要配置文件：
  - 插件总配置：定义运行参数、MES 路径、码表、诊断通道等。
  - 固定开发设备样本不单独拆 JSON，直接由 `Samples/` 下的播种器内置默认值；确有多套样本需求时先确认，不默认新增配置文件。
- 实体和运行代码按文件夹组织，避免把多个职责塞进同一个大文件。
- 运行时代码统一按以下结构组织：
  - `Runtime/`：放插件运行态 `Context`、PLC 信号编解码器、运行时工厂等共享运行部件。
  - `Runtime/Tasks/`：放进站、出站、配方、设备状态、心跳、实时快照等任务。
  - `Config/Hardware/`：放插件 PLC 信号枚举、`IModulePlcSignalProfile<TSignalKey>` 实现和 `IModuleHardwareProfileProvider` 实现。
  - `Config/Parameters/`：放插件参数枚举，只允许 `MesParam.cs`、`CloudParam.cs`、`BusinessParam.cs` 三类。
  - `Samples/`：放 `IDevelopmentSampleContributor` 实现和开发样本 Options。
  - 不要把任务散落在 `Runtime/` 根目录，也不要在每个任务只有一个文件时提前拆过多业务子目录。
- 业务数据、snapshot、PLC 信号、payload、context 字段必须留在对应插件内，不上提到宿主或共享层。

## 插件参数

插件参数按 MES、云端、业务三类拆分。插件只声明枚举和元数据，宿主负责注册、页面渲染、数据库读写、缓存、防击穿、类型转换和变更失效。

固定文件位置：

- `Config/Parameters/MesParam.cs`
- `Config/Parameters/CloudParam.cs`
- `Config/Parameters/BusinessParam.cs`

固定注册方式：

```csharp
builder.RegisterParameters<MesParam, CloudParam, BusinessParam>();
```

固定读取方式：

```csharp
var parameters = await _params.GetAsync(cancellationToken);

if (parameters.Business<bool>(BusinessParam.启用托盘码重码验证))
{
    // 插件只使用快照，不直接访问数据库或缓存。
}

var mesUrl = parameters.Mes<string>(MesParam.服务地址);
var mesEnabled = parameters.Mes<bool>(MesParam.启用);
```

参数枚举成员必须通过 `ModuleParamAttribute` 声明值类型、默认值、单位、范围和标准角色。标准角色只表达通用链路能力，例如 `MesEnabled`、`MesBaseUrl`、`StationNo`、`CloudEnabled`，不能承载具体工序业务逻辑。

插件参数存储 key 由宿主统一生成，格式为：

```text
Module:{ModuleId}:Mes:{Name}
Module:{ModuleId}:Cloud:{Name}
Module:{ModuleId}:Business:{Name}
```

插件代码禁止直接操作 `SystemConfigEntity`、`ILocalParameterConfigService`、`IEdgeCacheService` 或数据库。需要参数时注入 `IModuleParamProvider<MesParam, CloudParam, BusinessParam>`，一次读取快照，后续只通过 `Mes<T>`、`Cloud<T>`、`Business<T>` 做泛型读取。

参数配置页只保留 `MES 参数`、`云端参数`、`业务参数` 三个入口；业务参数只来自插件 `BusinessParam` 枚举。设备参数不再作为独立参数页入口，插件业务参数禁止放进 `SharedKernel` 枚举，只能通过 `Config/Parameters/` 下的三类枚举声明。

硬件配置页只负责网络设备、串口设备和 IO 映射。插件硬件模板通过 `Config/Hardware/` 提供插件标准点位和校验规则，宿主页面不得展示“模块协议汇总”这类文本摘要块；新增点位必须明确区分“信号交互”“单点读数据”“连续读数据”。IO 映射页面只按 `Category` 做一级分组，`BusinessGroup` 只能作为行内业务说明和排序辅助，不能拼成“信号交互 - 心跳交互”这类碎片标题。

IO 映射唯一真实来源是硬件配置中按每台 PLC 保存的 `IoMappingEntity`。插件的 `*PlcSignalProfile` 只能作为“导入插件标准点位”和开发播种的标准模板；运行任务、IO 交互页、诊断页都必须读取当前 PLC 的已保存映射，禁止直接读取插件模板或 JSON 点位源作为运行地址。开发样本禁止再维护 `mappings` 点位数组；固定样本设备也不应为了“可配置”额外拆一个 JSON。

插件 PLC profile 必须按业务含义拆分标准点位分组，例如信号交互、托盘信息、实时数据、配方数据、出料数据、设备状态/报警等，再通过统一的 `Signals` 汇总出口提供给硬件模板和开发播种。禁止把所有点位堆在一个扁平列表里，也禁止再新增独立 JSON 点位播种源。读取长度属于插件业务定义：单点数据通常为 1，连续数据和批量信号交互的长度必须由插件 profile 或本地映射明确声明，宿主不得写全局默认业务长度。

IO 分类语义固定如下：

- `信号交互`：只用于实时 PLC→PC 读取和 PC→PLC 写入的握手/应答类信号。地址一般连续，允许少量空洞；运行时会按插件 `PlcIoRuntimePolicy` 合并同地址族块读写，空洞由策略决定补零或拆块。
- `单点读数据`：用于业务任务按需读取的单个数据点，例如某个状态值或计数值；不进入实时信号交互循环。
- `连续读数据`：用于业务任务按需读取的连续数组或字符串，例如扫码、配方数组、批量参数；不进入实时信号交互循环。

PLC 信号访问接口和插件任务基类放在 `IIoT.Edge.Application` / `IIoT.Edge.Runtime`，PLC 通讯适配、IO 扫描任务基类和物理块规划归属 `IIoT.Edge.Infrastructure.DeviceComm`。插件只声明 `enum` 信号键并实现 profile；运行任务必须注入 `ILogicalSignalAccessor<TSignalKey>` 后用枚举读写，例如 `signals.ReadUInt16(HomogenizationSignal.进站触发)`。运行态缓存以 `SignalKey` 为强绑定键，业务任务不得依赖 `SortOrder` 累加 offset 或物理块数组下标。禁止新增 static profile 字段、string label 运行时访问、任务内手算 offset 或任务内直接拼 PLC 地址。基础设施项目只负责具体 PLC 通讯、扫描循环实现和状态上报，不得承载具体工序业务。

## 通用缓存

`IEdgeCacheService` 是客户端通用缓存基础设施，不是参数专用能力。新增高频查询场景必须优先复用 `GetOrCreateAsync`，不要为某个业务再造一套缓存框架。

- 同一个 key 的并发加载必须走 `GetOrCreateAsync` 单飞机制，避免缓存击穿。
- 数据库不存在的空结果允许短缓存，默认 30 秒。
- 保存、删除、批量覆盖后必须删除对应缓存 key 或 prefix。
- 后续产能记录、诊断摘要、设备信息等高频查询可以按同一缓存模型接入；本约定不要求本轮迁移这些业务。

## 任务模型

- 扫码进站、出站上传、配方上传、设备状态上传、心跳等都是独立任务。
- 每个任务只处理自己的 PLC 触发、采集、应答和复位。
- 触发-应答类 PLC 任务必须使用显式 `switch (Step)` 任务机，让现场调试能直接看到任务处于待触发、业务处理还是等待复位。
- 心跳镜像、周期快照上传这类没有业务阶段切换的任务，才优先继承 `HeartbeatMirrorPlcTaskBase`、`PeriodicSnapshotUploadTaskBase<TSnapshot>` 等共享任务基类。
- 任务之间不通过 `DeviceBag` 字符串 key 协作。
- 任务协作只能走插件自己的强类型 `Context` 和强类型字段或字典。

## 上传与 UI 注册

- 云端上传优先继承 `CloudUploadChannelBase<TCellData, TPayload>`，插件只保留字段映射和 payload 构建。
- MES 上传优先继承 `MesScenarioChannelBase<TCellData, ...>` 并复用 `MesRequestExecutor`，插件只保留路径、payload builder 和业务校验。
- MES 与云端上传必须继续保持两套链路、两套诊断、两套补偿语义，不能因为共用基类而混库或混通道。
- 标准页面优先使用共享导航注册扩展；只有真实存在插件业务展示逻辑时才新增 ViewModel。
- 不允许为了传 `viewId/title/moduleId` 单独创建空壳 ViewModel。

## 强类型 Context

- 需要运行态共享数据时，插件定义自己的派生上下文，例如 `ProcessContext`。
- 派生上下文必须由 `ProductionContextStore` 按模块和设备创建，不能用 DI 单例绕开宿主上下文。
- `Last*` 最近状态字段用于运行展示和分析，本约定不要求跨重启持久化。
- `DeviceBag` 只作为宿主内部临时诊断扩展点，不作为插件任务协作机制，也不作为新功能兼容层。

## 多电芯并发模型

后续新增的多电芯并发工序统一使用双字典模型。

```csharp
public sealed class ProcessContext : ProductionContext
{
    public ConcurrentDictionary<int, string> PlcIdToBarcode { get; } = new();

    public ConcurrentDictionary<string, ProcessCellData> Cells { get; } = new(StringComparer.Ordinal);
}
```

- `PlcIdToBarcode` 保存 PLC 循环 ID 到条码的映射。
- `Cells` 保存条码到强类型 `CellData` 的映射。
- 多个独立任务通过 PLC ID 或条码定位同一个电芯，并逐步补全数据。
- 上传完成后必须移除对应条码数据和 PLC ID 映射。

典型流程：

1. 扫码任务生成或接收 PLC 循环 ID，并建立 `PlcIdToBarcode[id] = barcode`。
2. 前工序任务收到 PLC ID 后查条码，创建或获取 `Cells[barcode]`，补前工序数据。
3. 后工序任务收到 PLC ID 后查条码，再查 `Cells[barcode]`，补后工序数据。
4. 出料或末道上传完成后，移除 `Cells[barcode]` 和 `PlcIdToBarcode[id]`。

## 重码规则

- PLC ID 重复：必须打印追溯日志，记录旧条码、新条码、设备、任务和时间；允许替换为新映射，保证生产不中断。
- 条码重复：不允许替换已有电芯数据；必须卡住当前任务，写入失败应答或人工处理状态，并提示人工确认。
- 条码重复不能用清空字典、覆盖 value、跳过校验等方式绕过。

## 匀浆例外

- 匀浆当前不是多电芯并发模板。
- 匀浆没有电芯条码字典，不把托盘码伪装成电芯 key。
- 匀浆任务可以记录最近托盘码、最近快照和出料记录，但不引入 `Cells` 字典。
- 匀浆出料是唯一进入本地补传和数据管道的通道。
