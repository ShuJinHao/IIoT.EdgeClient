# 插件开发约定

本文档是 EdgeClient 插件开发的固定约定。宿主可以复杂，插件必须保持简单，并且只能遵守一套入口规范。

## 模块入口

- 插件入口类型只能实现 `IEdgeProcessModule`。
- 插件只在 `Configure(IEdgeProcessModuleBuilder builder)` 中向宿主声明能力。
- 模块 ID、工序类型、显示名、服务注册、`CellData` 注册、运行时任务工厂、上传器、UI 注册都通过 `IEdgeProcessModuleBuilder` 完成。
- 不允许新增旧接口、适配器、过渡层或多套入口分支，除非用户明确要求。

## 客户端/云端分离开发硬规则

当前阶段客户端和云端分开开发。EdgeClient 默认只处理客户端通用框架、插件接入、运行时任务、上传抽象、本地补偿、诊断和启动项配置；不得因为 Cloud 上传、端到端闭环、审计建议、Assumptions 或测试便利去修改 `IIoT.CloudPlatform`。

- 客户端任务中可以先实现通用 Cloud channel、payload mapper、retry/fallback/deadletter 接入，但不能自行补云端 endpoint、事件、worker、SQL、迁移或查询框架。
- 云端上传对齐必须作为后续单独任务处理，并且需要用户明确授权当前任务允许修改云端。
- 新增工序时，插件按匀浆模块的结构方式开发，业务模型留在插件内；宿主只通过 `IEdgeProcessModuleBuilder`、模块注册和 launcher profile 识别新工序。
- 如果用户只要求客户端开发，最终 diff 不允许出现 `IIoT.CloudPlatform` 路径；发现云端已有其他改动时，只记录状态，不回退、不覆盖、不顺手修。

## 插件接入宿主流程

新增工序只接入客户端时，默认不修改云端项目，也不把客户端需求扩展成云边联动改造。若确实需要云端接口、云端表或云端查询支持，必须作为单独任务先与用户确认。

插件接入宿主按以下顺序执行：

1. 在 `src/Modules/IIoT.Edge.Module.<Process>` 下建立插件项目，插件入口继承 `EdgeProcessModuleBase<TCellData>` 或直接实现 `IEdgeProcessModule`。
2. 在插件入口中固定声明 `ModuleId`、`ProcessType`、`DisplayName`、Cloud 上传模式，以及需要时的 MES 上传模式。
3. 通过 `IEdgeProcessModuleBuilder` 注册插件能力：`CellData`、运行时工厂、Cloud/MES 上传器、硬件模板、开发样本、标准页面和必要的插件配置。
4. 运行任务由插件自己的 `IStationRuntimeFactory` 创建，任务只依赖宿主提供的 PLC buffer、强类型 Context、DataPipeline、日志和共享基类。
5. 工序菜单、页面和面板通过插件自己的导航注册扩展加入宿主，`ViewId` 必须以模块 ID 开头，不允许注册 `Core.*`。
6. 启动器不为某个工序单独写 XAML。启动项来自 `launcher.profiles.json`，该文件由 `scripts/edge-runtime.publish.json` 和生成脚本维护。

插件接入宿主时禁止以下做法：

- 禁止在宿主启动、导航、DataPipeline、PLC runtime 中硬编码某个工序的业务分支。
- 禁止绕过 `IEdgeProcessModuleBuilder` 直接写宿主注册表或静态全局表。
- 禁止把插件 payload、PLC 信号、Context、任务状态机、Cloud/MES 字段映射上提到宿主或共享层。
- 禁止在客户端插件任务中修改云端项目、云端接口、云端表结构或云端查询。

## 文件结构

- 一个插件代表一个工序，例如匀浆、注液、叠片。
- 每个插件保留两份配置文件：
  - IO 种子配置：定义 PLC 信号模板。
  - 插件总配置：定义运行参数、MES 路径、码表、诊断通道等。
- 实体和运行代码按文件夹组织，避免把多个职责塞进同一个大文件。
- 运行时代码统一按以下结构组织：
  - `Runtime/`：放插件运行态 `Context`、PLC 信号编解码器、运行时工厂等共享运行部件。
  - `Runtime/Tasks/`：放进站、出站、配方、设备状态、心跳、实时快照等任务。
  - `Config/Hardware/`：放 `IModuleHardwareProfileProvider` 实现和 PLC 信号模板定义。
  - `Samples/`：放 `IDevelopmentSampleContributor` 实现和开发样本 Options。
  - 不要把任务散落在 `Runtime/` 根目录，也不要在每个任务只有一个文件时提前拆过多业务子目录。
- 业务数据、snapshot、PLC 信号、payload、context 字段必须留在对应插件内，不上提到宿主或共享层。

## 任务模型

- 扫码进站、出站上传、配方上传、设备状态上传、心跳等都是独立任务。
- 每个任务只处理自己的 PLC 触发、采集、应答和复位。
- 触发-应答类 PLC 任务必须使用显式 `switch (Step)` 任务机，让现场调试能直接看到任务处于待触发、业务处理还是等待复位。
- 心跳镜像、周期快照上传这类没有业务阶段切换的任务，才优先继承 `HeartbeatMirrorPlcTaskBase`、`PeriodicSnapshotUploadTaskBase<TSnapshot>` 等共享任务基类。
- 任务之间不通过 `DeviceBag` 字符串 key 协作。
- 任务协作只能走插件自己的强类型 `Context` 和强类型字段或字典。

## 上传与 UI 注册

- 云端上传优先继承 `CloudUploadChannelBase<TCellData, TPayload>`，插件只保留字段映射和 payload 构建。
- MES 上传优先继承 `MesScenarioChannelBase<TCellData, ...>` 并复用 `MesRequestExecutor`，插件只保留路径、payload builder 和业务校验。
- MES 与云端上传必须继续保持两套链路、两套诊断、两套补偿语义，不能因为共用基类而混库或混通道。
- 标准页面优先使用共享导航注册扩展；只有真实存在插件业务展示逻辑时才新增 ViewModel。
- 不允许为了传 `viewId/title/moduleId` 单独创建空壳 ViewModel。

## 强类型 Context

- 需要运行态共享数据时，插件定义自己的派生上下文，例如 `InjectionContext`、`StackingContext`。
- 派生上下文必须由 `ProductionContextStore` 按模块和设备创建，不能用 DI 单例绕开宿主上下文。
- `Last*` 最近状态字段用于运行展示和分析，本约定不要求跨重启持久化。
- `DeviceBag` 只作为宿主过渡期兼容能力，不作为插件任务协作机制。

## 多电芯并发模型

注液、叠片等多电芯并发工序统一使用双字典模型。

```csharp
public sealed class InjectionContext : ProductionContext
{
    public ConcurrentDictionary<int, string> PlcIdToBarcode { get; } = new();

    public ConcurrentDictionary<string, InjectionCellData> Cells { get; } = new(StringComparer.Ordinal);
}
```

- `PlcIdToBarcode` 保存 PLC 循环 ID 到条码的映射。
- `Cells` 保存条码到强类型 `CellData` 的映射。
- 多个独立任务通过 PLC ID 或条码定位同一个电芯，并逐步补全数据。
- 上传完成后必须移除对应条码数据和 PLC ID 映射。

典型流程：

1. 扫码任务生成或接收 PLC 循环 ID，并建立 `PlcIdToBarcode[id] = barcode`。
2. 前工序任务收到 PLC ID 后查条码，创建或获取 `Cells[barcode]`，补前工序数据。
3. 后工序任务收到 PLC ID 后查条码，再查 `Cells[barcode]`，补后工序数据。
4. 出料或末道上传完成后，移除 `Cells[barcode]` 和 `PlcIdToBarcode[id]`。

## 重码规则

- PLC ID 重复：必须打印追溯日志，记录旧条码、新条码、设备、任务和时间；允许替换为新映射，保证生产不中断。
- 条码重复：不允许替换已有电芯数据；必须卡住当前任务，写入失败应答或人工处理状态，并提示人工确认。
- 条码重复不能用清空字典、覆盖 value、跳过校验等方式绕过。

## 匀浆例外

- 匀浆当前不是多电芯并发模板。
- 匀浆没有电芯条码字典，不把托盘码伪装成电芯 key。
- 匀浆任务可以记录最近托盘码、最近快照和出料记录，但不引入 `Cells` 字典。
- 匀浆出料是唯一进入本地补传和数据管道的通道。
