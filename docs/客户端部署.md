# EdgeClient 客户端部署

> 读取边界：日常 Edge 发布只读“0. 工作区标准入口”和本次受影响的 Host/Plugin 小节；未命中的安装、恢复、历史状态和现场验收章节不默认读取。

本文档是 EdgeClient 日常本机快发的项目级补充说明。本文中的“部署”固定指：在 Mac 本机构建 Windows 安装器、宿主、Velopack 更新或独立插件产物，经 Cloud HTTP 发布接口上传到生产服务器受控下载目录并登记 release，随后验证 Windows 下载链接；它不是把程序远程安装到某一台 Windows，也不经过 Harbor。上传部署总口径见 `../../docs/上传部署总览.md`；可选 GitHub 离线 artifact 与安装更新验收见 `docs/Edge安装更新验收.md`。

Edge 标准发布固定分三步：开发阶段用 `Validate-Candidate.ps1` 生成同 SHA 绿色证据；`Prepare-Release.ps1` 从 clean、已推送 main 生成并封存 Host/AP/CP 产物；`Deploy-Changed.ps1 -PreparedReleaseId <id>` 只上传预制包并验证 catalog/hash/download。正式 Deploy 不运行任何测试、CI、编译或 pack，不创建提交、不编辑文件。

用户明确说“赶生产”“立刻上线”或“紧急生产”时走 `Deploy-ProductionNow.ps1 -Target Edge`：不运行测试或 CI，先封存 Host/SDK/Private Plugins 当前字节，再只 pack 一次并上传；失败归档本轮新版本，旧 Published 继续生效，结果不得进入绿色基线。

三端从零部署从工作区根执行 `pwsh ./deploy/Deploy-FromZero.ps1 -Targets Cloud,AICopilot,Edge -ConfirmFromZero -PreparedReleaseId <id>`。Host/AP/CP 必须在 Cloud 清空前全部准备完成；清空后只签发 Release API key、上传预制包并验证下载链，不再构建。绝不创建设备、注册 `ClientCode` 或轮换设备 bootstrap secret。Host `installer-artifact.json` 可合法包含 `modules: []`，Host installer/Setup/Velopack 与 AP/CP 独立 zip 必须分别验收。

> 当前状态（2026-07-22）：三仓影响映射、SDK 唯一兼容门、Private Plugins 唯一 pack 调用、Host API 代际版本门和 Launcher 组合升级保护已进入候选；最终兼容门、三仓 push、真实 Cloud `stable` 上传/catalog/DB/静态 HEAD 与 Windows 下载/实机结果以本批最新滚动复盘和发布交接为准，任何未实际执行项不得称已验收。

## 0. 工作区标准入口

标准发布在工作区根执行：

```powershell
pwsh ./deploy/Validate-Candidate.ps1 `
  -Targets Edge `
  -BaselineEdgeHostSha <host-production-sha> `
  -BaselineEdgeSdkSha <sdk-production-sha> `
  -BaselineEdgePluginSha <plugin-production-sha>
pwsh ./deploy/Prepare-Release.ps1 `
  -Targets Edge `
  -BaselineEdgeHostSha <host-production-sha> `
  -BaselineEdgeSdkSha <sdk-production-sha> `
  -BaselineEdgePluginSha <plugin-production-sha> `
  -EdgeReleaseNotesPath ./release-notes.md
pwsh ./deploy/Deploy-Changed.ps1 -Targets Edge -PreparedReleaseId <prepared-release-id>
```

紧急生产：

```powershell
pwsh ./deploy/Deploy-ProductionNow.ps1 `
  -Target Edge `
  -Components Host,AP,CP `
  -EdgeReleaseNotesPath ./release-notes.md `
  -ConfirmProductionNow PRODUCTION_NOW
```

`LocalPublishAndDeploy.ps1 -PrepareOnly` 和 `PublishEdgePluginRelease.ps1 -PrepareOnly` 只负责 Prepare；`Deploy-EdgePrepared.ps1` 只负责上传。它们不是 AI 或操作者复制执行的第二套公开入口。

工作区顶层入口向 Edge 内部执行器传递 `Deploy`、`ProfilePath`、release notes、Cloud token 等公共命名参数时，必须使用 PowerShell 命名 hashtable splatting；字符串数组 splatting 是位置绑定，不得用来表达命名参数。

## 1. 发布边界

- EdgeClient 不走 Docker、Harbor 或 GHCR。
- 生产服务器只发布 `stable` 渠道。
- 多 AI/多终端并行时只允许通过工作区统一入口竞争同一 Edge 本地发布锁；未取得锁的一方必须在构建前停止，不能并行调用项目实现脚本。
- EdgeHost 与 EdgePlugin 共用本地发布互斥锁；一个 AI 正在构建或上传时，另一个 AI 必须在构建前立即看到 active lock 并停止。进程已消失或 PID 启动时间不一致的 stale lock 由下一次发布回收。
- 正式发布必须在构建前确认工作树 clean 且 HEAD 已推送到 upstream；`-AllowDirty` 只允许 validate/dry-run，不能用于 deploy。
- 入口执行前后必须证明 tracked 文件零变化；任何并发或收尾改动都停止，部署任务不得编辑、提交或修复。
- 日常快发在操作者本机完成编译、Velopack 打包、installer artifact 生成和验证，然后通过 Cloud Human API 受控 HTTP 上传到 `${EDGE_UPDATES_DIR}`。
- HTTP 上传默认限速 `1000 Mbps`、单并发、服务端审计，并在完成后输出部署总结和 HTTP 验证结果。
- 当前生产现场口径中，`${EDGE_UPDATES_DIR}` 标准值是 `/data/iiot-platform/edge-client/edge-updates`；历史 `/srv/iiot/edge-updates` 只保留给旧 `scp/rsync` 或非生产 fallback 说明，不再是当前标准 HTTP 路径。
- catalog、HTTP 上传和静态 HEAD 验证都必须带连接、总时限和低速停滞门禁；`4xx/5xx` 响应正文必须进入错误摘要。本机构建、打包或上传失败时保留 `edge-deployment-attempt.json`、bundle/wrapper 和已验证产物，通过统一入口传 `-ResumeReleaseRoot` 只做复核、重传或已发布对账，不得反复从头全量构建。
- 更新内容必须显式填写；本机快发必须传 `-ReleaseNotes` 或 `-ReleaseNotesPath`。GitHub 离线 artifact 的 notes 不能替代生产 release notes。
- 生产 `stable` 发布必须走 HTTP API。`LocalPublishAndDeploy.ps1` 不再允许 stable 走 `rsync` 或 `scp`，避免绕过 Cloud DB、审计、保留策略和更新内容校验。
- 只改工序插件时，不发布宿主；内部使用 `scripts/PublishEdgePluginRelease.ps1 -PluginRepositoryRoot <workspace>/IIoT.Edge.Plugins.Private` 调用插件仓唯一 pack，只上传插件 zip 并登记插件 release。
- Host bundle 必须保持业务中立，不得包含或代为登记 CP/AP 等具体工序插件。Host 与 Plugin 同时受影响时分别发布，source commit 分别归属各自仓；不得再以“Host bundle 已包含插件”为由跳过插件发布。
- 当前生产插件发布目标只允许 `CP` 与 `AP`。Homogenization 已退役，不得从旧缓存、旧 package 或历史 release 目录重建、上传或恢复到活动 catalog；必要历史审计只由 Cloud 归档保留。
- 从零恢复历史后，profile 的 `retiredModuleIds=["Homogenization"]` 必须由统一入口通过 Cloud Human API 把仍活动的版本改为 `Archived`；不得删除历史版本、说明、哈希或审计记录。
- SDK Contracts/Module.Sdk/UI.Shared 或 SDK build 输入变化至少影响 Host，并在发布前运行 SDK 仓唯一兼容门；Analyzer 与纯文档 SDK 变化不得发布 Host/Plugin。兼容门必须绑定三仓 clean HEAD、正式 SDK 包、Private Plugins 唯一 zip 和生产不可变组合字节。
- 发布脚本只移动安装器素材和 Velopack 更新文件，不修改数据库卷、Cloud 账号、设备绑定或现场数据。
- Cloud 下载中心、catalog 和首装版本集合只来自 Cloud release 记录；服务器文件系统只校验已登记 `installer-artifact.json` 和包文件的存在性、完整性与可下载性，不得扫描目录补出版本。生成带设备绑定的最终安装包仍由 Cloud 负责。

## 2. 本机依赖

- PowerShell 7：`pwsh`
- .NET SDK 10
- 原生 `curl`
- Cloud 发布凭据：日常发布只从 macOS Keychain canonical Edge Release API key 换短期发布 JWT，不读取 Markdown、旧 env 或 Human session fallback。Cloud 管理员创建 key 时权限只给 `ClientRelease.Read` / `ClientRelease.Publish`，明文只在创建响应里返回一次并立即写入 Keychain。

如果本机还没有发布 API key，可由具备 `ClientRelease.Manage` 的 Cloud 账号一次性创建并保存：

```powershell
pwsh ./scripts/InitializeEdgeReleaseApiKey.ps1 `
  -CloudApiBaseUrl http://<cloud-gateway-host>:<port>/api/v1 `
  -EmployeeNo <employee-no>
```

如果 Cloud 管理员已经单独创建好 key，本机只保存该 key：

```powershell
pwsh ./scripts/SaveEdgeReleaseApiKey.ps1 `
  -CloudApiBaseUrl http://<cloud-gateway-host>:<port>/api/v1
```

初始化后，日常部署命令直接读取 macOS Keychain。显式 `-CloudToken` 只允许受控恢复；`IIOT_CLOUD_RELEASE_TOKEN`、`IIOT_EDGE_RELEASE_API_KEY`、旧 Human session、Markdown 和旧 env 都不是标准部署 fallback。`scripts/InitializeEdgeReleaseApiKey.ps1` 登录 Human 账号只用于一次性创建 API key，不保存 Human refresh token。

## 2.1 部署前只读检查

任何宿主或插件正式发布前，统一入口先运行 preflight。这个脚本只读检查文档入口、release notes、Cloud token、Cloud 健康、插件 manifest 和 git 状态，不生成包、不上传服务器。

工作区身份必须 fail closed：在标准 `<WorkspaceRoot>/IIoT.EdgeClient` canonical checkout 中运行时可以省略 `-WorkspaceRoot`；从 linked worktree 单独运行只读 preflight 时，必须显式传入顶层工作区的绝对 `-WorkspaceRoot`。该根必须同时包含 `docs/上传部署总览.md` 与 `deploy/Invoke-WorkspaceDeploy.ps1` 两个 marker，且当前 checkout 必须与 `<WorkspaceRoot>/IIoT.EdgeClient` 归属同一个 git common dir。相对路径、marker 缺失、canonical checkout 无效或 repository owner 不一致均以 `EDGE-DEPLOY-WORKSPACE-001` 拒绝；路径别名按物理身份核对。`-WorkspaceRoot` 只提供只读检查所需的工作区上下文，不授权部署、上传、发布或生产操作，也不替代工作区统一入口。

因此，下列示例在 canonical checkout 中无需额外参数；若从 linked worktree 执行同一只读诊断，应在命令中追加 ``-WorkspaceRoot <顶层工作区绝对路径>``。

宿主本机快发：

```powershell
pwsh ./scripts/TestEdgeDeploymentPreflight.ps1 `
  -Mode Host `
  -CloudApiBaseUrl http://<cloud-gateway-host>:<port>/api/v1 `
  -ReleaseNotesPath ./release-notes.md
```

插件独立发布：

```powershell
pwsh ./scripts/TestEdgeDeploymentPreflight.ps1 `
  -Mode Plugin `
  -ModuleId <ModuleId> `
  -PluginRepositoryRoot <workspace-root>/IIoT.Edge.Plugins.Private `
  -CloudApiBaseUrl http://<cloud-gateway-host>:<port>/api/v1 `
  -ReleaseNotesPath ./release-notes.md
```

GitHub `edge-pack-modules.yml` 只生成离线 Actions artifact，不是部署入口，不连接 Cloud，也没有对应的生产 preflight mode。需要标准发布时，先从工作区根完成 Validate/Prepare，再用 `Deploy-Changed.ps1 -Targets Edge -PreparedReleaseId <id>` 投放。

preflight 失败时不进入发布命令。`HTTP 400 hash/size` 不一致时，先对比下载后的 artifact 文件列表、`installer-artifact.json` 和 Cloud 服务端校验算法；优先复用已生成 artifact 或重跑失败 job，不要直接反复全量 CI。

## 3. 宿主发布命令

宿主构建只发生在 Prepare：

```powershell
pwsh ./deploy/Prepare-Release.ps1 `
  -Targets Edge `
  -BaselineEdgeHostSha <host-production-sha> `
  -BaselineEdgeSdkSha <sdk-production-sha> `
  -BaselineEdgePluginSha <plugin-production-sha> `
  -EdgeReleaseNotesPath ./release-notes.md
```

Prepare 的 signed manifest 固定版本、source commit、release root、SHA256 和 size。正式上传或上传失败后的恢复都使用同一个 prepared release：

```powershell
pwsh ./deploy/Deploy-Changed.ps1 `
  -Targets Edge `
  -PreparedReleaseId <prepared-release-id>
```

不得用旧 `Invoke-WorkspaceDeploy.ps1 -Target EdgeHost` 在生产窗口重新构建。

## 4. 插件独立发布

只改某个工序插件时，Validate/Prepare 的影响闭包只选择对应 ModuleId，不递增宿主版本。正式上传仍消费 prepared release：

```powershell
pwsh ./deploy/Deploy-Changed.ps1 `
  -Targets Edge `
  -PreparedReleaseId <prepared-release-id>
```

prepared manifest 中的 `ModuleId` 没有默认值；缺失时 Prepare 必须失败，不能从任何示例 profile 静默选择模块。插件上传失败只能重用同一 prepared release，不得重新 pack。

生产执行时 `ModuleId` 当前只允许显式选择 `CP` 或 `AP`；退役模块即使本机存在旧产物也不得作为发布输入。

脚本会执行：

- 调用 Private Plugins 仓唯一 `eng/PackEdgePlugin.ps1`，从该仓 clean commit 生成独立插件 zip 和 schema v2 metadata；`sourceCommit` 必须等于插件仓 HEAD。
- 校验 Cloud catalog 中不存在相同 `(moduleId, channel, version, targetRuntime)`，重复版本直接失败，要求先提升 `plugin.json` 版本。
- 上传到 `POST /api/v1/human/client-releases/plugin-packages`。
- Cloud 将插件包落到 `${EDGE_UPDATES_DIR}/plugins/stable/<ModuleId>/<version>/`，写 `edge_client_plugin_releases`，并按 SemVer 对 stable 最新 3 个版本执行保留策略。
- 输出兼容窗口、下载 URL、sha256、包大小和更新内容。

## 5. 自动版本规则

- `-Version` 已传入时，脚本严格使用传入值。
- `-Version` 未传入时，HTTP 发布会先读取 Cloud Human catalog 下最新 stable SemVer 版本。
- 读取到 `1.0.6` 时，下一版本自动为 `1.0.7`。
- 当候选 `hostApiVersion` 与已发布 Host API 不同时禁止自动 patch；必须显式传入与新 API 代际相同的首个 Host 产品版本，例如 `hostApiVersion=2.0.0` 必须使用 `-EdgeHostVersion 2.0.0`。
- Cloud 不可达、catalog 超时、HTTP 失败、结构缺失或版本解析失败时必须在构建前停止，禁止 fallback 到 `0.0.1`。只有 catalog 请求成功且明确返回真实空版本列表的首次发布才允许使用 `0.0.1`。
- GitHub 离线 artifact 不参与生产 catalog 版本递增，也不得把输入版本写成已发布版本。

## 6. 发布摘要

快发脚本会写入 `installer-artifact.json`：

- `sourceCommit`：本次发布的 EdgeClient git commit。
- `previousVersion`：服务器上读取到的上一 stable 版本；首次发布可为空。
- `previousSourceCommit`：上一 stable artifact 记录的 commit；旧 artifact 没有该字段时可为空。
- `releaseNotes`：必须来自操作者显式填写的 `-ReleaseNotes` 或 `-ReleaseNotesPath`，不能为空，不能用自动 git log 代替人工发布说明。
- `generatedAtUtc`：artifact 生成时间。

Cloud 下载中心读取该 artifact 后可以展示版本和更新内容。旧下载包不会自动变新，客户端安装验证必须重新从 Cloud 下载中心下载。

HTTP 发布成功后，服务端还会返回发布摘要。脚本必须打印版本、commit、更新内容、上传耗时、限速、落盘路径、归档/清理结果和静态下载验证结果。

## 7. 服务器目录

逻辑目录结构如下；生产现场真实根目录以 Cloud `.env` 的 `EDGE_UPDATES_DIR` 为准，不在客户端脚本或文档中固化某台服务器 IP。

```text
${EDGE_UPDATES_DIR}/
  installers/stable/<version>/
    installer-artifact.json
    IIoT.Edge.Setup.exe
    launcher/
    host/
    velopack/
  velopack/stable/
    releases.stable.json
    assets.stable.json
    *.nupkg
    *-Setup.exe
    *-Portable.zip
  plugins/stable/<ModuleId>/<version>/
    IIoT.EdgePlugin.<ModuleId>-<version>-<runtime>.zip
```

HTTP 发布由 Cloud 服务端执行保留策略：每个 stable/runtime/component 按 SemVer 最多保留最新 3 次发布；已归档且无设备在用的旧安装素材才会回收。宿主 bundle 只含 Host/Launcher/Installer/Velopack，不生成、不覆盖也不登记业务插件；插件只来自 Private Plugins 独立发布。EdgeClient 不存在 Docker/Harbor 镜像，不参与 Cloud/AICopilot 应用镜像清理。

## 8. 验收命令

HTTP 快发会自动执行静态下载检查。需要人工复核时，使用 Cloud 返回的 `verificationUrls` 或当前环境的下载域名，不在文档中固化服务器 SSH 地址。

```bash
curl --fail --head '<edge-download-base-url>/edge-updates/installers/stable/<version>/installer-artifact.json'
```

静态下载检查：

```bash
curl -o /dev/null -w '%{http_code} %{size_download}\n' \
  '<edge-download-base-url>/edge-updates/installers/stable/<version>/IIoT.Edge.Setup.exe'
```

返回 `200` 且下载大小大于 0，才说明 nginx 静态链路可用。

Cloud catalog 需要登录态；未登录返回 `401` 不代表版本不可见。

## 9. 常见失败

- `-Transport rsync/scp`：stable 生产发布已禁止，改用 `-Transport http` 并提供 Cloud token。
- HTTP 上传返回 `409`：已有发布上传正在执行，稍后重试。
- HTTP 上传返回 `413`：Cloud/Gateway/nginx 大包限制未同步放开。
- 插件发布提示版本已存在：提升插件项目 `plugin.json` 的 `version` 后重新打包发布。
- HTTP 上传很慢：确认 `-UploadRateLimitMbps`，当前默认 1000 Mbps；如果仍慢，继续看本地 build、Velopack/installer 生成、Cloud 落盘校验和静态下载验证。
- 构建或上传超时：查看统一摘要和保留目录中的 `edge-deployment-attempt.json`，确认失败阶段后用 `-ResumeReleaseRoot` 复核/重传，不要反复全量构建；检查摘要中的 HTTP 状态与受限响应正文、Cloud token、manifest hash/size、Cloud/Gateway/nginx 日志和 `${EDGE_UPDATES_DIR}` 真实挂载。
- Edge Release API key 被拒绝：确认 Cloud 已部署 `/api/v1/machine/edge-release/token`，key 未吊销、未过期，并具备 `ClientRelease.Read` / `ClientRelease.Publish`；重新运行 `scripts/InitializeEdgeReleaseApiKey.ps1` 创建并保存新 key，或运行 `scripts/SaveEdgeReleaseApiKey.ps1` 保存 Cloud 管理员已创建的 key。不要把 API key、管理员密码、access token 或 refresh token 写入仓库、release notes、shell profile 或文档。
- Human refresh token 401：这是旧 fallback 被 Cloud 会话上限逐出的典型表现，不要反复要求部署人重新输入账号密码；改用 Edge Release API key 稳定发布通道。
- 服务器或 catalog 不可达：必须在构建前失败，先恢复 Cloud Human API；不得 fallback 到 `0.0.1` 或先做昂贵构建。
- Cloud 下载中心看不到版本：先确认 Cloud DB 中存在对应 `Published` release，再核对该记录登记的 installer artifact、静态文件和 `${EDGE_UPDATES_DIR}` 挂载；残留文件不会自动补出版本。
- Windows 安装器提示缺少 Velopack Setup：必须重新从 Cloud 下载中心下载最新生成的安装包，不能继续使用旧下载包。

## 10. 首次 HTTP 发布踩坑记录

2026-06-22 首次端到端跑 Cloud HTTP 发布链路时暴露以下脚本问题，后续发布脚本修改必须避免重演：

- `Set-StrictMode -Version Latest` 下读取可选字段前必须判断属性存在，例如 `description`、`CloudApi`、`PluginModuleId`。
- `installer-artifact.json` 的目录 hash 必须使用和 Cloud 一致的 Ordinal 排序；本地 smoke test 也必须使用同一算法。
- 失败后优先复用已生成的 installer artifact / Velopack 产物重新上传，不要每次从头全量构建。
- HTTP 上传 `400 hash/size 不一致` 先查 manifest 算法和 bundle 布局；`401` 先刷新 Cloud token；`502` 要结合 nginx 和 httpapi 日志确认真实上游状态。
- 稳定发布脚本不得放宽 release notes、DB 登记、审计或保留策略来“先跑起来”。
