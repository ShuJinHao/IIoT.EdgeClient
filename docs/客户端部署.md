# EdgeClient 客户端部署

本文档是 EdgeClient 日常本机快发的项目级补充说明。本文中的“部署”固定指：在 Mac 本机构建 Windows 安装器、宿主、Velopack 更新或独立插件产物，经 Cloud HTTP 发布接口上传到生产服务器受控下载目录并登记 release，随后验证 Windows 下载链接；它不是把程序远程安装到某一台 Windows，也不经过 Harbor。上传部署总口径见 `../../docs/上传部署总览.md`，GitHub 正式打包和安装更新验收见 `docs/Edge安装更新验收.md`。

操作者或 AI 的 Edge 日常唯一正式入口是从工作区根执行 `pwsh ./deploy/Deploy-Changed.ps1 -Targets Edge`，只读规划使用同一入口加 `-PlanOnly`。入口自动 push 已提交的 `main`、读取服务器已发布基线，只在宿主受影响时发布宿主，只在具体模块受影响时发布对应插件。只有检测到 Edge 产物需要发布时才要求显式 `-EdgeReleaseNotes` 或 `-EdgeReleaseNotesPath`。`deploy/Invoke-WorkspaceDeploy.ps1` 只允许被该入口内部调度，或在故障恢复时显式传入 `-ResumeReleaseRoot`；不是普通验证、日常快发或正式发布命令。本文件里的 `scripts/*.ps1` 继续作为被调度实现脚本。

> 当前状态（2026-07-10）：隔离提交 `37ec98b` 的发布行为 19/19、Host/Plugin 恢复链 12/12、发布契约 2/2 已通过；本轮没有执行真实 Cloud `stable` 上传/catalog/DB/静态 HEAD，也没有执行 Windows 安装/更新实机验收，因此不得称生产发布已验收。

## 0. 工作区标准入口

操作者或 AI 需要先只读查看本次 Edge 影响计划时，在工作区根执行：

```powershell
pwsh ./deploy/Deploy-Changed.ps1 -Targets Edge -PlanOnly
```

计划确认后的日常正式命令仍使用同一根入口：

```powershell
pwsh ./deploy/Deploy-Changed.ps1 -Targets Edge -EdgeReleaseNotesPath ./release-notes.md
```

`Invoke-WorkspaceDeploy.ps1`、`LocalPublishAndDeploy.ps1`、`PublishEdgePluginRelease.ps1` 是内部实现，不是给操作者或 AI 复制执行的备用入口；除显式 `-ResumeReleaseRoot` 恢复外，缺少统一入口生成的 target、invocation id 和内部调度标记时必须拒绝执行。

## 1. 发布边界

- EdgeClient 不走 Docker、Harbor 或 GHCR。
- 生产服务器只发布 `stable` 渠道。
- 多 AI/多终端并行时只允许通过工作区统一入口竞争同一 Edge 本地发布锁；未取得锁的一方必须在构建前停止，不能并行调用项目实现脚本。
- EdgeHost 与 EdgePlugin 共用本地发布互斥锁；一个 AI 正在构建或上传时，另一个 AI 必须在构建前立即看到 active lock 并停止。进程已消失或 PID 启动时间不一致的 stale lock 由下一次发布回收。
- 正式发布必须在构建前确认工作树 clean 且 HEAD 已推送到 upstream；操作者或 AI 的只读计划只使用根入口 `-PlanOnly`，不得把内部 `-AllowDirty` / `-ValidateOnly` 当作第二入口。
- 日常快发在操作者本机完成编译、Velopack 打包、installer artifact 生成和验证，然后通过 Cloud Human API 受控 HTTP 上传到 `${EDGE_UPDATES_DIR}`。
- HTTP 上传默认限速 `1000 Mbps`、单并发、服务端审计，并在完成后输出部署总结和 HTTP 验证结果。
- 当前生产现场口径中，`${EDGE_UPDATES_DIR}` 标准值是 `/data/iiot-platform/edge-client/edge-updates`；历史 `/srv/iiot/edge-updates` 只保留给旧 `scp/rsync` 或非生产 fallback 说明，不再是当前标准 HTTP 路径。
- catalog、HTTP 上传和静态 HEAD 验证都必须带连接、总时限和低速停滞门禁；`4xx/5xx` 响应正文必须进入错误摘要。本机构建、打包或上传失败时保留 `edge-deployment-attempt.json`、bundle/wrapper 和已验证产物，通过统一入口传 `-ResumeReleaseRoot` 只做复核、重传或已发布对账，不得反复从头全量构建。
- 更新内容必须显式填写；本机快发必须传 `-ReleaseNotes` 或 `-ReleaseNotesPath`，正式 GitHub 打包必须填写 `release_notes` 或使用带正文的 annotated tag。
- 生产 `stable` 发布必须走 HTTP API。`LocalPublishAndDeploy.ps1` 不再允许 stable 走 `rsync` 或 `scp`，避免绕过 Cloud DB、审计、保留策略和更新内容校验。
- 只改工序插件时，不发布宿主；根入口只能在内部调度 `scripts/PublishEdgePluginRelease.ps1` 上传插件 zip 并登记插件 release，操作者或 AI 不得直接执行该脚本。
- 发布脚本只移动安装器素材和 Velopack 更新文件，不修改数据库卷、Cloud 账号、设备绑定或现场数据。
- Cloud 下载中心、catalog 和首装版本集合只来自 Cloud release 记录；服务器文件系统只校验已登记 `installer-artifact.json` 和包文件的存在性、完整性与可下载性，不得扫描目录补出版本。生成带设备绑定的最终安装包仍由 Cloud 负责。

## 2. 本机依赖

- PowerShell 7：`pwsh`
- .NET SDK 10
- 原生 `curl`
- Cloud 发布凭据：日常发布使用 Edge Release API key 换短期发布 JWT，不再依赖 Human refresh token 会话。Cloud 管理员先用具备 `ClientRelease.Manage` 的 Human token 调用 `/api/v1/human/client-release-api-keys` 创建 key，权限只给 `ClientRelease.Read` / `ClientRelease.Publish`，明文只在创建响应里返回一次。操作者本机保存该 key 后，发布脚本会自动换取短期 JWT。

如果本机还没有发布 API key，可由具备 `ClientRelease.Manage` 的 Cloud 账号一次性创建并保存：

```powershell
pwsh ./scripts/InitializeEdgeReleaseApiKey.ps1 `
  -CloudApiBaseUrl http://<cloud-gateway-host>:<port>/api/v1 `
  -EmployeeNo <employee-no>
```

如果 Cloud 管理员已经单独创建好 key，本机只保存该 key：

```powershell
pwsh ./scripts/SaveEdgeReleaseApiKey.ps1 `
  -CloudApiBaseUrl http://<cloud-gateway-host>:<port>/api/v1
```

初始化后，日常部署命令不需要再传 `-CloudToken`，除非要临时覆盖本机凭据。解析顺序固定为：显式 `-CloudToken`、`$env:IIOT_CLOUD_RELEASE_TOKEN`、`$env:IIOT_EDGE_RELEASE_API_KEY` 或 macOS Keychain 中的 Edge Release API key、旧 Human session fallback。`scripts/InitializeEdgeReleaseApiKey.ps1` 登录 Human 账号只用于一次性创建 API key，不保存 Human refresh token；`scripts/SaveEdgeReleaseToken.ps1` 只作为创建/管理 key 前的临时 Human 应急通道，不再作为稳定发布入口。

## 2.1 部署前只读检查

任何宿主、插件或 GitHub 正式发布前，先运行 preflight。这个脚本只读检查文档入口、release notes、Cloud token、Cloud 健康、workflow 包名、manifest normalize 步骤、插件 manifest 和 git 脏状态，不生成包、不上传服务器。

宿主本机快发：

```powershell
pwsh ./scripts/TestEdgeDeploymentPreflight.ps1 `
  -Mode Host `
  -CloudApiBaseUrl http://<cloud-gateway-host>:<port>/api/v1 `
  -ReleaseNotesPath ./release-notes.md
```

插件独立发布：

```powershell
pwsh ./scripts/TestEdgeDeploymentPreflight.ps1 `
  -Mode Plugin `
  -ModuleId DieCuttingAnode `
  -CloudApiBaseUrl http://<cloud-gateway-host>:<port>/api/v1 `
  -ReleaseNotesPath ./release-notes.md
```

GitHub 正式宿主发布：

```powershell
pwsh ./scripts/TestEdgeDeploymentPreflight.ps1 `
  -Mode GitHubHost `
  -Version 1.0.16 `
  -CloudApiBaseUrl http://<cloud-gateway-host>:<port>/api/v1 `
  -ReleaseNotesPath ./release-notes.md
```

preflight 失败时不进入发布命令。`HTTP 400 hash/size` 不一致时，先对比下载后的 artifact 文件列表、`installer-artifact.json` 和 Cloud 服务端校验算法；优先复用已生成 artifact 或重跑失败 job，不要直接反复全量 CI。

## 3. 宿主发布调度

工作区根入口会先跑影响计划和 preflight，再在确认宿主受影响时用内部调度标记调用项目脚本。操作者或 AI 不手工选择 `EdgeHost`，仍只执行：

```powershell
pwsh ./deploy/Deploy-Changed.ps1 -Targets Edge -EdgeReleaseNotesPath ./release-notes.md
```

默认宿主版本由内部分发器按 catalog 自动递增。上传或静态验证失败且摘要给出保留目录时，才允许使用下列显式恢复命令；它只复用该目录，不重新构建：

```powershell
pwsh ./deploy/Invoke-WorkspaceDeploy.ps1 `
  -Target EdgeHost `
  -ReleaseNotesPath ./release-notes.md `
  -ResumeReleaseRoot <absolute-preserved-release-root>
```

## 4. 插件独立发布

只改某个工序插件时，工作区根入口会从 Git 影响自动识别真实 `ModuleId`、调度独立插件发布且不递增宿主版本。操作者或 AI 仍只执行：

```powershell
pwsh ./deploy/Deploy-Changed.ps1 -Targets Edge -EdgeReleaseNotesPath ./release-notes.md
```

内部调度的 `ModuleId` 没有默认值；无法从差异唯一归属真实模块时根入口必须失败，不能从任何示例 profile 静默选择模块。插件上传失败后，只有摘要给出保留目录时才能显式调用内部分发器并传 `-ResumeReleaseRoot`，同时必须传原真实 `-ModuleId`。

脚本会执行：

- 调用 `PackEdgePlugin.ps1` 生成独立插件 zip 和 metadata。
- 校验 Cloud catalog 中不存在相同 `(moduleId, channel, version, targetRuntime)`，重复版本直接失败，要求先提升 `plugin.json` 版本。
- 上传到 `POST /api/v1/human/client-releases/plugin-packages`。
- Cloud 将插件包落到 `${EDGE_UPDATES_DIR}/plugins/stable/<ModuleId>/<version>/`，写 `edge_client_plugin_releases`，并按 SemVer 对 stable 最新 3 个版本执行保留策略。
- 输出兼容窗口、下载 URL、sha256、包大小和更新内容。

## 5. 自动版本规则

- `-Version` 已传入时，脚本严格使用传入值。
- `-Version` 未传入时，HTTP 发布会先读取 Cloud Human catalog 下最新 stable SemVer 版本。
- 读取到 `1.0.6` 时，下一版本自动为 `1.0.7`。
- Cloud 不可达、catalog 超时、HTTP 失败、结构缺失或版本解析失败时必须在构建前停止，禁止 fallback 到 `0.0.1`。只有 catalog 请求成功且明确返回真实空版本列表的首次发布才允许使用 `0.0.1`。
- GitHub tag 打包流程不使用这套自动递增规则，tag 本身就是正式版本号。

## 6. 发布摘要

快发脚本会写入 `installer-artifact.json`：

- `sourceCommit`：本次发布的 EdgeClient git commit。
- `previousVersion`：服务器上读取到的上一 stable 版本；首次发布可为空。
- `previousSourceCommit`：上一 stable artifact 记录的 commit；旧 artifact 没有该字段时可为空。
- `releaseNotes`：必须来自操作者显式填写的 `-ReleaseNotes` 或 `-ReleaseNotesPath`，不能为空，不能用自动 git log 代替人工发布说明。
- `generatedAtUtc`：artifact 生成时间。

Cloud 下载中心读取该 artifact 后可以展示版本和更新内容。旧下载包不会自动变新，客户端安装验证必须重新从 Cloud 下载中心下载。

HTTP 发布成功后，服务端还会返回发布摘要。脚本必须打印版本、commit、更新内容、上传耗时、限速、落盘路径、归档/清理结果和静态下载验证结果。

## 7. 服务器目录

逻辑目录结构如下；生产现场真实根目录以 Cloud `.env` 的 `EDGE_UPDATES_DIR` 为准，不在客户端脚本或文档中固化某台服务器 IP。

```text
${EDGE_UPDATES_DIR}/
  installers/stable/<version>/
    installer-artifact.json
    IIoT.Edge.Setup.exe
    launcher/
    host/
    plugins/
    velopack/
  velopack/stable/
    releases.stable.json
    assets.stable.json
    *.nupkg
    *-Setup.exe
    *-Portable.zip
  plugins/stable/<ModuleId>/<version>/
    IIoT.EdgePlugin.<ModuleId>-<version>-<runtime>.zip
```

HTTP 发布由 Cloud 服务端执行保留策略：每个 stable/runtime/component 按 SemVer 最多保留最新 3 次发布；已归档且无设备在用的旧安装素材才会回收。宿主 bundle 发布会为缺失登记的插件版本生成独立 zip；已登记的同版本插件不会被宿主发布覆盖。EdgeClient 不存在 Docker/Harbor 镜像，不参与 Cloud/AICopilot 应用镜像清理。

## 8. 验收命令

HTTP 快发会自动执行静态下载检查。需要人工复核时，使用 Cloud 返回的 `verificationUrls` 或当前环境的下载域名，不在文档中固化服务器 SSH 地址。

```bash
curl --fail --head '<edge-download-base-url>/edge-updates/installers/stable/<version>/installer-artifact.json'
```

静态下载检查：

```bash
curl -o /dev/null -w '%{http_code} %{size_download}\n' \
  '<edge-download-base-url>/edge-updates/installers/stable/<version>/IIoT.Edge.Setup.exe'
```

返回 `200` 且下载大小大于 0，才说明 nginx 静态链路可用。

Cloud catalog 需要登录态；未登录返回 `401` 不代表版本不可见。

## 9. 常见失败

- `-Transport rsync/scp`：stable 生产发布已禁止，改用 `-Transport http` 并提供 Cloud token。
- HTTP 上传返回 `409`：已有发布上传正在执行，稍后重试。
- HTTP 上传返回 `413`：Cloud/Gateway/nginx 大包限制未同步放开。
- 插件发布提示版本已存在：提升插件项目 `plugin.json` 的 `version` 后重新打包发布。
- HTTP 上传很慢：确认 `-UploadRateLimitMbps`，当前默认 1000 Mbps；如果仍慢，继续看本地 build、Velopack/installer 生成、Cloud 落盘校验和静态下载验证。
- 构建或上传超时：查看统一摘要和保留目录中的 `edge-deployment-attempt.json`，确认失败阶段后用 `-ResumeReleaseRoot` 复核/重传，不要反复全量构建；检查摘要中的 HTTP 状态与受限响应正文、Cloud token、manifest hash/size、Cloud/Gateway/nginx 日志和 `${EDGE_UPDATES_DIR}` 真实挂载。
- Edge Release API key 被拒绝：确认 Cloud 已部署 `/api/v1/machine/edge-release/token`，key 未吊销、未过期，并具备 `ClientRelease.Read` / `ClientRelease.Publish`；重新运行 `scripts/InitializeEdgeReleaseApiKey.ps1` 创建并保存新 key，或运行 `scripts/SaveEdgeReleaseApiKey.ps1` 保存 Cloud 管理员已创建的 key。不要把 API key、管理员密码、access token 或 refresh token 写入仓库、release notes、shell profile 或文档。
- Human refresh token 401：这是旧 fallback 被 Cloud 会话上限逐出的典型表现，不要反复要求部署人重新输入账号密码；改用 Edge Release API key 稳定发布通道。
- 服务器或 catalog 不可达：必须在构建前失败，先恢复 Cloud Human API；不得 fallback 到 `0.0.1` 或先做昂贵构建。
- Cloud 下载中心看不到版本：先确认 Cloud DB 中存在对应 `Published` release，再核对该记录登记的 installer artifact、静态文件和 `${EDGE_UPDATES_DIR}` 挂载；残留文件不会自动补出版本。
- Windows 安装器提示缺少 Velopack Setup：必须重新从 Cloud 下载中心下载最新生成的安装包，不能继续使用旧下载包。

## 10. 首次 HTTP 发布踩坑记录

2026-06-22 首次端到端跑 Cloud HTTP 发布链路时暴露以下脚本问题，后续发布脚本修改必须避免重演：

- `Set-StrictMode -Version Latest` 下读取可选字段前必须判断属性存在，例如 `description`、`CloudApi`、`PluginModuleId`。
- `installer-artifact.json` 的目录 hash 必须使用和 Cloud 一致的 Ordinal 排序；本地 smoke test 也必须使用同一算法。
- 失败后优先复用已生成的 installer artifact / Velopack 产物重新上传，不要每次从头全量构建。
- HTTP 上传 `400 hash/size 不一致` 先查 manifest 算法和 bundle 布局；`401` 先刷新 Cloud token；`502` 要结合 nginx 和 httpapi 日志确认真实上游状态。
- 稳定发布脚本不得放宽 release notes、DB 登记、审计或保留策略来“先跑起来”。
